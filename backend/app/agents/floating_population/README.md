# 인구 분석 에이전트 (`floating_population`)

주소 하나를 받아 그 주변의 **유동인구(오가는 사람)·주거인구(사는 사람)·직장인구(일하는 사람)**를
서울 평균과 비교해 정리하고, 결정 에이전트가 읽기 좋은 형태로 넘긴다. 에이전트 id·폴더 이름은
처음 이름 그대로 `floating_population` 이다.

**점수를 내지 않고 업종을 고르지 않는다.** 업종 판단은 결정 에이전트의 일이고, 이 에이전트는
그 판단에 쓸 **분포·서울 대비 지표·해석 문장**까지만 책임진다.

## 한눈에 보기

```
AnalysisTask(주소 좌표 + 반경)
  │
  ├─ ① 반경과 겹치는 상권 고르기 ─────── 상권영역 API · 면적 등가원 · 반경의 절반까지만 인정
  │
  ├─ ② 자료 준비
  │     ├ 유동인구   서울시 API · 최근 4개 분기 · 분기당 2페이지(동시 수신)
  │     └ 주거·직장  동봉한 CSV(data/resident.csv · data/worker.csv) · API 호출 없음
  │
  ├─ ③ 유동인구 계산 ─── 합산·분포 → 유형 판정 → 서울 대비 지표 → 추세 → 반경 곡선 → 신뢰도
  ├─ ④ 주거·직장 계산 ── 같은 상권만 합산 → 서울 기준선(파일에서 계산) → 인구 총괄
  ├─ ⑤ 해석 문장 ─────── 위 숫자를 규칙으로 풀어 쓴 5~8줄 + 근거 경로
  ├─ ⑥ 선별 (LLM) ────── 결정 에이전트 입력에서 뺄 차트용 블록만 고른다 · 실패하면 전부 싣는다
  │
  └─ AgentAnalysis(status · scope · data · warnings)
```

- **호출 규모.** 분석 한 번에 서울시 API 약 12회(최신 분기 탐침 · 상권영역 · 유동인구 4개
  분기), 선별 LLM 1회. 실측 약 3초. 주거·직장인구는 패키지에 동봉한 CSV 를 읽는다 — 아래
  「주거·직장인구는 CSV 로 동봉한다」.
- **숫자는 전부 코드가 계산한다.** LLM 은 ⑥에서 블록을 고르기만 한다. 유형 판정(③)·구성
  판정(④)·해석 문장(⑤)도 규칙 기반이라 같은 입력이면 항상 같은 결과가 나온다.
- **상권 선택은 한 번만 한다.** 세 인구가 같은 상권 집합을 쓰므로 분모가 어긋나지 않는다.
  회의에서 배정된 "상주·직장·총괄 에이전트 3개" 를 별도 에이전트가 아니라 `data` 안 블록
  3개로 낸 이유다(팀 합의).

## 입출력

팀 공용 계약(`app/schemas.py`)만 쓴다.

```
AnalysisTask ─▶ analyze() ─▶ AgentAnalysis
```

```python
from app.agents.floating_population import analyze
from app.schemas import AnalysisTask, Site

analysis = await analyze(
    AnalysisTask(
        request_id="...",
        site=Site(
            input_address="서울특별시 강남구 역삼동 ...",
            road_address="서울특별시 강남구 테헤란로 ...",
            latitude=37.5006,
            longitude=127.0365,
        ),
        radius_m=500,  # 생략하면 500. 분석 반경은 이 값만 따른다
    )
)
```

**반경은 `AnalysisTask.radius_m` 이 정한다.** `Settings.analysis_radius_m`·`ANALYSIS_RADIUS_M`
은 예제 스크립트 호환용으로 남아 있을 뿐 분석에 쓰이지 않는다.

**비동기다.** 오케스트레이터가 분석 에이전트를 `asyncio.gather` 로 동시에 돌린다
(`AnalysisAgent = Callable[[AnalysisTask], Awaitable[AgentAnalysis]]`). `client` 를 주입하지
않으면 `analyze()` 가 만들고 끝날 때 닫는다. 직접 관리하려면
`async with SeoulOpenDataClient(settings) as c: await analyze(task, client=c)` 를 쓴다.

**예외를 던지지 않는다.** 세 분석 에이전트가 병렬로 돌아 하나가 예외를 던지면 전체가 죽는다.
모든 실패는 계약 `status` 로 나온다.

| status | 언제 | `data` |
| --- | --- | --- |
| `ok` | 겹치는 상권 전부의 유동인구를 확보하고 주거·직장 파일도 읽음 | 있음 |
| `partial` | 유동인구가 일부 상권만 있음, 또는 주거·직장 파일을 읽지 못함 | 있음(확보된 만큼만) |
| `no_data` | 겹치는 상권이 없거나, 해당 분기 유동인구 자료가 없음 | 비어 있음 |
| `error` | 상권영역·유동인구 API 오류·시간 초과·키 누락 | 비어 있음 + `error` |

주거·직장인구는 **보조 자료**라 파일이 없거나 깨져도 `error` 로 번지지 않는다 — 그 블록만
`null` 이 되고 `partial` + warnings. 반면 **반경 안 상권에 자료가 원래 없는 것**(시장·역 상권은
주거인구가 없다)은 누락이 아니라 사실이므로 블록은 `null` 이어도 `ok` + warnings 다. 파일 읽기
중 형식 오류가 아닌 예외(코드 버그)는 숨기지 않고 그대로 올린다.

## 단계별로

**① 상권 고르기** (`geo.py`) — 서울시 상권분석서비스의 "상권" 은 시가 그은 분석 구역이라
반경 검색이 없다. 상권영역(약 1,650곳)을 받아 위경도를 EPSG:5181 로 바꾸고(`app/geo.py`),
구역을 면적이 같은 원으로 근사해 반경과 겹치는지 본다. 등가 반지름은 반경의 절반까지만
인정한다(`geo._MAX_AREA_REACH_RATIO = 0.5`) — 근거는 아래 「알려진 한계」.

**② 자료 준비** (`client.py` · `population.py`) — 유동인구는 오늘 분기부터 거꾸로 탐침해 자료가
있는 최신 분기를 찾고 4개 분기를 동시에 받는다. 주거·직장인구는 API 를 부르지 않고 동봉한
`data/resident.csv`·`data/worker.csv`(최신 분기 서울 전체)를 읽는다.

**③ 유동인구** (`metrics.py` · `classify.py` · `baseline.py`) — 고른 상권을 합산해 연령·시간대·
요일 분포를 내고, 4유형(주거생활형·직장인형·여가상업형·학생형) 중 하나로 추정하고, 서울 평균
대비 배수(`benchmark`)·분기 추세(`trend`)·반경 안쪽 곡선(`radius_profile`)·신뢰도를 계산한다.
유동인구 서울 기준선은 2026Q2 실측 상수다.

**④ 주거·직장·총괄** (`population.py`) — 유동인구와 같은 분기 코드의 행을 고르고(없으면 파일의
분기로 물러서며 warnings), 같은 상권만 합산한다. 서울 기준선은 파일의 서울 전체 행에서 바로
계산한다. 총괄은 세 자료가 모두 있는 상권만으로 비율을 내고 직장/주거 비로 구성을 판정한다.

**⑤ 해석 문장** (`interpret.py`) — 핵심 숫자를 "점심(11~14시) 시간당 통행 비중이 서울 평균의
1.34배로 가장 두드러진다." 같은 문장으로 풀고, 문장마다 근거 값의 JSON Pointer(`path`)를 단다.

**⑥ 선별** (`llm.py` · `prompt.md`) — 결정 에이전트 프롬프트에서 뺄 수 있는 차트용 블록 넷 중
무엇을 뺄지 모델이 고른다. 원본 `data` 는 그대로 저장·반환되고, 실패하면 전부 싣는다.

| 파일 | 역할 |
| --- | --- |
| `agent.py` | 흐름 조립. 실패를 status 로 바꾸는 유일한 곳 |
| `client.py` | 서울 열린데이터광장 API. 영문 컬럼을 아는 곳은 여기와 `models.py` 뿐 |
| `models.py` | API 응답 한 행 → 파이썬 객체. 데이터셋 개편 시 여기만 고친다 |
| `geo.py` | 반경과 상권 구역의 겹침 판정·면적 안분. 좌표 투영은 `app/geo.py` |
| `metrics.py` | 유동인구 합산·서울 대비 지표·추세·반경 곡선·신뢰도 |
| `classify.py` | 유동인구 유형 판정 규칙과 임계치 |
| `baseline.py` | 유동인구 서울 기준선(2026Q2 실측 상수) |
| `population.py` | 주거·직장인구 스냅샷 읽기·쓰기, 집계, 서울 기준선, 인구 총괄 |
| `data/resident.csv` · `data/worker.csv` | 주거·직장인구 최신 분기 스냅샷(서울 전체) |
| `interpret.py` | 해석 문장(규칙 기반) |
| `llm.py` · `prompt.md` | 넘길 블록 선별(숫자는 만들지 않는다) |
| `schemas.py` | `data` 본문의 자료 구조 — 키 이름이 곧 결정 에이전트와의 인터페이스 |
| `config.py` | 설정값(`Settings`) |

## `data` 안에 무엇이 들어가고, 왜 그것인가

`data` 는 계약상 자유 형식이지만 **소비 경로가 둘**이다. 최종 판단은 추천 근거를 만들고,
프론트엔드는 SQLite에 저장된 `DecisionResult.source_analyses`를 POST/GET API로 받아 차트와 표를
만든다. 별도 report 에이전트는 없다. 그래서 판단용 지표와 화면용 원시 시리즈를 둘 다 담는다.

| 키 | 소비자 | 내용 |
| --- | --- | --- |
| `description` | 결정 | 이번 요청의 사실(상권 수·도달 거리·분기)과 프롬프트에 없는 주의만 담은 짧은 설명 |
| `interpretation` | 결정·화면 | 숫자의 핵심을 풀어 쓴 문장 목록(`text` + 근거 `path`). 코드 규칙으로 생성 |
| `population` | 화면 | 연령·시간대·요일 분포 원시값과 비중 |
| `benchmark` | 결정 | 서울 평균 대비 상대지표(1.0 = 평균) |
| `trend` | 결정·화면 | 분기별 추세 4개 점 + 전분기 변화율(4개 분기라 전년 동기는 `null`) |
| `radius_profile` | 화면 | 분석 반경 **안쪽**을 단계별로 나눈 인구(면적 안분 추정값) |
| `type` | 결정·화면 | 유형 라벨 + 판정에 쓴 숫자(`signals`)와 임계치 |
| `reliability` | 결정 | 표본이 얼마나 두터운지 — 가중치를 낮추는 근거 |
| `resident` | 결정·화면 | 주거인구(사람 수) · 가구당 인원 · 연령 비중 · 서울 대비 지표 |
| `worker` | 결정·화면 | 직장인구(사람 수) · 연령 비중 · 서울 대비 지표 |
| `population_summary` | 결정·화면 | 세 인구의 비율(더하지 않음)과 주거/직장 구성 판정 |
| `trade_areas` | 화면 | 집계에 포함된 상권 — 거리·면적·등가 반지름·구분 |
| `selection` | 사람 | 무엇을 넘기고 무엇을 뺐는지, 왜 뺐는지 |
| `sources` | 화면 | 출처 표기 |

**`benchmark` 가 필요한 이유.** 절대 비중만 주면 판단이 안 된다. 시간대는 구간이 6개라
균등값이 0.167 이고, `11_14` 가 0.16 이라는 값만으로는 점심 수요가 높은지 낮은지 알 수 없다.
서울 평균 대비 배수로 주면 결정 에이전트가 바로 쓸 수 있다 — 실제로 역삼1동은
`lunch_index 1.336` · `weekend_index 0.639` 로, "직장인 점심 수요가 높다"가 숫자로 나온다.

**키 이름은 사실상 인터페이스다.** 결정 에이전트가 근거를 JSON Pointer 경로
(`Evidence.path`, 예: `/benchmark/lunch_index`)로 가리킨다. 그래서 `data` 를 자유 dict 가
아니라 `schemas.py` 의 모델로 고정했고, **키를 바꿀 때는 결정 에이전트 담당과 함께 바꾼다.**

## 화면에 무엇을 싣고, 무엇을 실으면 안 되는가

프론트엔드는 저장된 최종 판단의 `source_analyses`로 이 `data`를 받는다. 전부 보여줄 것은 아니다.
아래 표가 **이 에이전트가 사용자에게 보여줄 수 있다고 보증하는 것**이다.

### 실어도 되는 것

| 키 | 화면에서의 역할 | 길동 실제 값 |
| --- | --- | --- |
| `type.label` + `type.reasons` | 헤드라인 결론 | 주거생활형 / "50·60대 합 42%(서울 35%)" |
| `population.daily_avg` | 대표 숫자 | 174,179 명/일 |
| `population.age_share` | 연령 분포 차트 | 60대 25.8%, 20대 12.3% |
| `population.time_per_hour_share` | 시간대 차트 | 21~24시 18.1% 최대 |
| `population.by_day` | 요일 차트 | 일 234만 > 금 225만 |
| `population.female_ratio` | 성별 | 0.543 |
| `population.peak_time_band` | "가장 붐비는 시간" | `21_24` |
| `benchmark.age_index` | 서울 평균 대비 막대 | 60대 1.283, 20대 0.687 |
| `benchmark.lunch/evening/night/weekend_index` | 수요 시간대 판단 | 0.893 / 0.981 / 1.107 / 1.064 |
| `benchmark.scale_percentile` | 규모 뱃지 | 89 → "서울 상권 상위 11%" |
| `trend.quarters[].daily_avg` | 추세 꺾은선 | 4개 분기 (2025Q3~2026Q2) |
| `trend.direction` + `qoq_change` | 추세 한 줄 | 보합 / 직전 분기 대비 −4.6% (`yoy_change` 는 4개 분기라 `null`) |
| `radius_profile.points[].daily_avg` | 반경 단계별 인구 | 50m 1,787 → 500m 106,544 |
| `reliability.level` + `trade_area_count` | 신뢰도 표시 | high / 9곳 |
| `trade_areas[].name` | "어디를 집계했나" | 길동역, 길동복조리시장 … 9곳 |
| `sources` | 출처 표기 | 공공누리 1유형이라 **표기 의무** |

#### 해석 문장 (`interpretation`)

| 키 | 화면에서의 역할 | 역삼1동 실제 값 |
| --- | --- | --- |
| `interpretation[].text` | 요약 카드의 문장 그대로 | "점심(11~14시) 시간당 통행 비중이 서울 평균의 1.34배로 가장 두드러진다." |

`path` 는 화면에 보이지 않는 근거 값 위치다. 문장은 결정론적이라 같은 주소면 항상 같다.

#### 주거인구·직장인구·총괄 (1.5 MVP 추가)

| `resident.persons_per_household` | "1인가구 동네 / 가족 동네" | 1.961 명/가구 (서울 1.76) |
| `resident.age_share` | 주거인구 연령 차트 | 60대 이상 비중 |
| `worker.count` | "일하는 사람" 대표 숫자 | 10,837 명 |
| `worker.age_share` | 직장인구 연령 차트 | 50·60대 비중 |

### 실으면 안 되는 것

- **주거·직장인구를 유동인구와 더한 값** — 유동인구는 통행량(중복 집계), 주거·직장은 사람
  수다. "총 인구 22만" 같은 합계를 만들지 않는다. 나란히 보여주되 단위를 따로 적는다.
- **"현재 인구" 라는 표현** — 서울시가 2026년 2분기로 발행한 값이지만 원천이 연 1회도 채
  갱신하지 않는다(주거는 2023Q4, 직장은 2024Q4 이후 값이 같다). 기준 분기 그대로 표기한다.
- `population_summary.composition_rule` · `basis_trade_areas` · `*.benchmark.baseline` — 판정
  근거용 문장·숫자다.
- **`population.by_time` 원값** — ⚠️ **가장 위험한 자리다.** 총량 1위는 `00_06`(423만)인데
  그 구간이 6시간이라 그럴 뿐이다. 시간당으로 보면 `21_24` 가 1위다. `by_time` 을 그대로
  막대그래프로 그리면 **"길동은 새벽에 사람이 가장 많다"는 틀린 리포트**가 나온다.
  반드시 `time_per_hour_share` 를 쓴다.
- `description`(결정 에이전트 LLM 용 설명) · `type.signals`/`thresholds`/`rules_version` ·
  `*_unit` · `period_code` · `trade_areas[].code`/`area_m2`/`distance_m`/`equivalent_radius_m`
  — 전부 결정 판단용·내부 판정용이다.

### 같은 500m 인데 숫자가 둘인 이유

`population.daily_avg`(174,179)와 `radius_profile` 의 500m 점(106,544)은 다르다. 모순이 아니다.

- `population` 은 반경에 **걸친 상권을 구역째** 합산한다(그래서 바깥 경계가 925m 까지 간다).
  지역의 대표 수치는 이쪽이다.
- `radius_profile` 은 **겹친 면적만큼만** 센다. 반경에 따른 증가 추이를 보는 값이다.

리포트가 둘을 나란히 놓을 때는 축이나 캡션을 나눠야 한다.

## 해석 문장과 짧아진 설명 (`interpretation` · `description`)

결정 에이전트가 `data` 를 LLM 프롬프트로 읽는다. 숫자만 주면 단위·기준을 다시 추론해야 하고,
긴 설명을 주면 판단 지표가 묻힌다. 그래서 두 가지를 했다.

- **`interpretation` — 숫자를 풀어 쓴 문장 5~8줄.** `interpret.py` 가 규칙으로 만든다(LLM
  아님). 유형, 규모 백분위, 서울 대비 가장 두드러진 시간대·연령대, 주말/주중(평균에서 10%
  이상 벗어날 때만), 추세(전년 동기, 없으면 직전 분기 대비 — 기본 4개 분기에선 직전 분기),
  직장/주거 구성, 가구당 인원, 신뢰도가 낮을 때 그 사실. LLM 선별로 `trend` 가 빠지면 추세
  문장도 함께 뺀다(뺀 값을 문장으로 되살리지 않도록).
  문장마다 근거 값의 `path` 가 붙어 있어 결정 에이전트가 그대로 `evidence.path` 로 쓸 수
  있다(시험에서 모든 `path` 가 실제 값으로 풀리는지 확인한다). 업종 추천이나 원인 단정은
  넣지 않는다.
- **숫자 필드는 그대로 둔다.** 결정 에이전트는 근거를 필드 경로로 인용하고 코드가 그 경로를
  검증한다. 숫자를 문장으로만 넘기면 인용할 자리가 없어지고, 화면도 같은 숫자로 차트를 그린다.
- **`description` 을 약 1,090자 → 약 330자로 줄였다.** 요청마다 같은 해석 규칙(통행량,
  시간당 비교, 면적 안분, 추세 읽는 법, 선별)은 결정 프롬프트 「유동인구 해석」 절에 이미
  있어 뺐다. 이번 요청의 사실과 프롬프트에 아직 없는 주의(상권 조각의 뜻, 인구 블록끼리
  더하지 않기)만 남겼다. 각 블록 `unit` · `composition_rule` · `radius_profile.method` 도
  줄였다(`method` 는 화면 캡션이라 사람이 읽는 문장으로 유지).

세 지점 실측(2026Q2, 반경 500m) — 해석 문장을 더하고도 전체가 줄었다.

| 지점 | `data` 전체 | `description` | `interpretation` |
| --- | --- | --- | --- |
| 길동 | 9,626 → 8,991자 | 1,088 → 324자 | 609자 (6줄) |
| 역삼1동 | 9,514 → 8,958자 | 1,088 → 324자 | 688자 (7줄) |

## 주거인구·직장인구·인구 총괄 (`resident` · `worker` · `population_summary`)

회의 배정은 "상주인구·직장인구·인구총괄 에이전트 3개" 였고, **에이전트 3개 대신 `data`
안의 블록 3개**로 냈다(팀 합의). 에이전트를 쪼개면 상권영역 조회와 상권 선택이 세 벌이 되고,
셋이 미세하게 다른 상권을 고르면 같은 지역인데 인구의 분모가 달라진다. 지금은 **유동인구와
같은 상권 집합**을 한 번 고르고 데이터셋만 두 개 더 받는다.

- **데이터셋.** 상주인구-상권 `VwsmTrdarRepopQq`(OA-15584) · 직장인구-상권
  `VwsmTrdarWrcPopltnQq`(OA-15569). 같은 키로 열리고 둘 다 `TRDAR_CD` 단위다.
- **API 가 아니라 동봉한 CSV 를 읽는다.** 이유와 갱신 방법은 바로 아래 절.
- **기준선은 파일의 서울 전체 행에서 계산한다.** 상수로 박지 않는다 — `baseline.py` 가 분기
  갱신 때마다 낡는 문제가 여기엔 없다.
- **분기는 유동인구와 같은 코드**(`20262`)를 쓴다. 파일의 분기가 유동인구보다 뒤처지면 파일
  분기로 물러서고 warnings 에 적는다(= 스냅샷을 갱신할 때라는 신호). 값이 2~3년째 같아도
  서울시가 발행한 분기 그대로 쓴다(팀 결정 2026-09-22).
- **`APT_HSHLD_CO`(아파트 가구수)는 22개 분기 전 행이 0** 이라 쓰지 않는다. 대신
  **가구당 인원**(`TOT_REPOP_CO ÷ TOT_HSHLD_CO`, 서울 약 1.76명)으로 1인가구 동네와 가족
  동네를 가른다.
- **시장·역 상권은 주거인구가 없다.** `covered_trade_areas < trade_area_count` 면 warnings 에 적는다.
- **총괄은 비율만 낸다.** 세 자료가 모두 있는 상권(`basis_trade_areas`)만으로
  `visitor_multiple`(유동인구 명/일 ÷ 주거인구) · `worker_to_resident_ratio` 를 내고, 직장/주거
  비를 서울 평균(약 1.26)과 비교해 `composition` 을 정한다 — 1.5배 이상 직장 중심, 1/1.5 이하
  주거 중심, 그 사이 혼재.
- **`classify()` 에는 넣지 않는다.** 주거·직장인구는 유동인구 유형 판정의 **검증 정답**으로
  쓰던 값이라(`tools-local/fetch_ground_truth.py`), 입력에 넣으면 길동·역삼1동·서교동 라벨
  검증이 무의미해진다. `composition` 은 `type` 과 따로 서는 규칙이다.
- **실패해도 유동인구 분석은 나간다.** 파일을 읽지 못하면 그 블록(과 총괄)은 `null`, `status` 는
  `partial`, 이유는 warnings 에 적는다. 두 파일의 분기가 다르면 총괄 비율이 서로 다른 분기를
  나눈다는 사실을 warnings 에 적는다.
- **파일은 프로세스당 한 번만 읽는다.** 요청마다 다시 파싱하면 이벤트 루프를 약 30ms 막는다.
- **선별 대상이 아니다.** 세 블록 합쳐 작고 판단에 직접 쓰는 값이라 항상 싣는다.

## 주거·직장인구는 CSV 로 동봉한다

처음에는 분석마다 서울시 API 로 받았는데 두 가지 문제가 있었다.

- **요청이 너무 많았다.** Open API 는 요청 하나에 1,000행까지만 주고, 두 서비스는 경로의 분기
  필터가 먹지 않아(`20262` 를 붙여도 22개 분기 35,908행 전부) 한 분기를 쓰려고 매번 주거 36 +
  직장 37페이지를 받았다. 받은 것의 약 95% 를 버렸고 분석 한 번이 12~20초 걸렸다.
- **한꺼번에 보내면 실패했다.** 70여 개를 동시에 보내면 서울시 API 가 JSON 이 아닌 오류 응답을
  돌려주어 직장인구 블록이 비는 일이 실제로 있었다(동시 8개로 묶으면 오류 0건).

값은 2~3년째 같다(주거 2023Q4, 직장 2024Q4 이후 동일). 그래서 **최신 분기의 서울 전체 행만 CSV
로 동봉**하고 런타임에는 파일을 읽는다. `commercial_area` 의 `data/seoul_trade_areas.csv` 와 같은
방식이다. 분석 시간은 약 3초로 돌아왔고(같은 주소에서 23.4초 → 3.2초, 결과 동일) 주거·직장
쪽 네트워크 실패도 없어졌다.

| 파일 | 행 | 크기 | 컬럼 |
| --- | --- | --- | --- |
| `data/resident.csv` | 1,633 (2026Q2) | 137KB | 분기 · 상권코드·이름 · 총 주거인구 · 연령 6구간 · 총 가구 수 |
| `data/worker.csv` | 1,641 (2026Q2) | 122KB | 분기 · 상권코드·이름 · 총 직장인구 · 연령 6구간 |

컬럼 이름은 서울시 API 그대로다(`TOT_REPOP_CO` 등) — 같은 파서(`PopulationRecord.from_api_row`)로
읽고, 파일을 열어 서울시 문서와 바로 대조할 수 있다.

**갱신:** 서울시가 값을 바꾸면(연 1회 이하) 아래를 돌리고 바뀐 CSV 를 커밋한다. 에이전트가
"파일 분기가 유동인구 분기보다 뒤처졌다" 는 warnings 를 내기 시작하면 돌릴 때다.

```bash
python examples/fetch_population_snapshot.py   # 약 20초. 동시 8개 · 페이지별 재시도
```

두 자료를 **모두 받은 뒤에** 파일을 쓴다 — 하나만 새로 쓰고 실패하면 두 파일의 분기가 어긋난다.
행 수 상한은 두지 않는다(원자료가 분기순이 아니라 잘라내면 최신 분기 행이 무작위로 빠진다).

## 분기별 추세 (`trend`)

최신 1개 분기만 보던 단면 분석의 한계를 푼다. **같은 상권 집합**을 분기마다 다시 합산한다 —
반경 판정은 상권영역(시점 없는 현재 스냅샷)으로 한 번만 하므로 분기가 바뀌어도 대상은 같다.

- 기본 **4개 분기** — 최신 분기 + 최대 3분기 전까지(2026Q2 기준 2025Q3~2026Q2).
  원본에는 2021Q1 부터 22개 분기가 있지만 리포트에 필요한 건 최근 흐름뿐이다.
  `trend_quarters` 로 바꾼다.
- 분기끼리 의존이 없어 `asyncio.gather` 로 한꺼번에 받는다(약 1.2초).
- 변화율은 `daily_avg` 로 잰다. 분기 합계는 분기 일수(90~92일)가 달라 그대로 비교하면 최대 2%
  의 가짜 증감이 섞인다.
- `direction` 은 ±5% 밖이면 증가/감소, 안이면 보합이다. `yoy_change`(전년 동기)가 있으면
  계절성이 빠져 판단에 나으므로 그걸 먼저 쓰고, 없으면 `qoq_change`(전분기)로 판정한다.
  **⚠️ 4개 분기에서는 전년 동기가 4분기 전이라 `yoy_change` 가 항상 `null` 이다** — 전년 동기
  비교를 살리려면 `trend_quarters` 를 5 이상으로 올려야 한다.
- 계절성은 실재한다. 12개 분기로 재봤을 때 길동은 **1분기가 3년 연속 피크**였다(2024Q1 180,934 ·
  2025Q1 187,271 · 2026Q1 182,578 명/일). 4개 분기만 보면 이 주기가 안 보이므로, 전분기 대비
  증감을 계절 변동과 혼동하지 않도록 주의한다.
- 분기마다 자료가 있는 상권 수가 다르면 증감이 표본 변화일 수 있어 `trade_area_count` 를
  분기마다 함께 싣고, 값이 흔들리면 `warnings` 에 적는다.

## 반경 단계별 인구 (`radius_profile`) — 면적 안분 추정값이다

분석 반경을 **넓히는 게 아니라 안쪽을 쪼개서** 본다. 기본 단계 `50 · 100 · 200 · 300 · 400 · 500m`
중 분석 반경보다 작은 것만 쓰고, 분석 반경(`AnalysisTask.radius_m`) 자체를 마지막 점으로 붙인다
(반경 300m → `50 · 100 · 200 · 300`, 1,000m → `… · 400 · 500 · 1000`).

**대표 점 거리로 세면 작은 반경에서 아무것도 안 잡힌다.** 실측(2026Q2, 반경 500m 판정 상권 기준):

| 반경 | 길동(9곳) | 테헤란로(8곳) | 서교동(12곳) | 평창동(2곳) |
| --- | --- | --- | --- | --- |
| 50m | 0곳 | 0곳 | 0곳 | 0곳 |
| 100m | 0곳 | 1곳 | 0곳 | 0곳 |
| 200m | 0곳 | 1곳 | 0곳 | 0곳 |
| 300m | 3곳 | 1곳 | 1곳 | 0곳 |
| 400m | 4곳 | 2곳 | 3곳 | 0곳 |
| 500m | 5곳 | 4곳 | 6곳 | 1곳 |

(상권 대표 점이 그 반경 안에 든 개수. 서울시 상권은 구역이고 대표 점은 그 구역의 한 점일 뿐이다.)

300m 아래로는 네 지점 모두 0~1곳이라 **개수로 세는 방식은 성립하지 않는다.** 그래서 계산을
**면적 단위**로 한다 — 반경 원과 상권 면적 등가원의 **겹친 면적 비율**만큼만 인구를 센다
(`geo.circle_overlap_ratio`, 원-원 렌즈 교집합). 길동 결과:

| 반경 | 일평균 | 걸친 상권 | 안분 곳분 |
| --- | --- | --- | --- |
| 50m | 1,787 | 2곳 | 0.04 |
| 100m | 6,196 | 2곳 | 0.14 |
| 200m | 21,809 | 3곳 | 0.62 |
| 300m | 46,926 | 4곳 | 1.96 |
| 400m | 76,483 | 5곳 | 3.46 |
| 500m | 106,544 | 9곳 | 5.14 |

- **가정: 상권 안에서 인구가 고르게 분포한다.** 실측값이 아니라 추정값이므로 `method` 와
  `warnings` 에 밝힌다.
- **⚠️ 작은 반경일수록 추정 성격이 강하다.** 50m 의 `안분 곳분 0.04` 는 "상권 하나의 4%" 라는
  뜻이다 — 사실상 가장 가까운 상권의 인구 밀도에 원 넓이를 곱한 값이고, 면적이 반경² 에
  비례하므로 값도 그렇게 움직인다. 화면에서 50~100m 를 단독 수치로 강조하지 않는 게 좋다.
- **평창동은 50~100m 가 0 이다.** 버그가 아니라 저밀도라 걸치는 상권 구역이 실제로 없는
  것이다. 억지로 채우지 않는다.
- 지점을 늘리거나 줄여도 **API 호출은 늘지 않는다** — 전부 로컬 계산이다.

## 넘길 자료 선별 (`llm.py` · `prompt.md`)

`data` 원본은 반환·저장하고, 최종판단의 프롬프트 입력 복사본만 선별한다. 분석 에이전트가 셋이라
그대로 두면 판단에 쓸 지표가 차트용 시리즈에 묻힌다. 실측(길동, 2026Q2, 전체 8,991자):

| 블록 | 크기 | 비중 | 선별 대상 |
| --- | --- | --- | --- |
| `trend` | 1,402자 | 15.6% | ✅ |
| `trade_areas` | 1,305자 | 14.5% | ✅ |
| `radius_profile` | 843자 | 9.4% | ✅ |
| `population` | 817자 | 9.1% | 원값(`by_age`·`by_time`·`by_day`)만 ✅ |
| `resident` · `worker` · `population_summary` | 1,559자 | 17.3% | — |
| `sources` | 631자 | 7.0% | — |
| `interpretation` | 609자 | 6.8% | — |
| `benchmark` · `type` · `reliability` | 993자 | 11.0% | — |
| `description` | 324자 | 3.6% | — |

판단에 직접 쓰는 블록(`benchmark`·`type`·`reliability`·`interpretation`·인구 블록 셋)은 합쳐
3,161자, 전체의 35% 다. 선별로 차트용 블록을 모두 빼면 결정 에이전트 입력은 약 5,400자가 된다.

### 무엇을 고르나

모델이 고를 수 있는 블록은 **넷뿐**이다(`llm.SELECTABLE`):
`trade_areas` · `population_raw`(연령·시간대·요일 원값) · `radius_profile` · `trend`

`description`·`interpretation`·`benchmark`·`type`·`reliability`·`resident`·`worker`·
`population_summary`·`sources`와 비중 값들은 **선별 대상이 아니다.**
결정 에이전트가 점수와 근거를 만들 때 반드시 쓰므로 어떤 경우에도 빠지지 않는다.

### 규칙 셋

**① 숫자는 모델이 만들지 않는다.** 이미 코드가 계산한 블록 중 무엇을 실을지만 고른다.
고른 결과도 허용 목록 안인지 `parse_selection()` 이 다시 확인하고, 하나라도 어긋나면 응답을
통째로 버린다(`AGENTS.md` 4번).

**② 실패하면 전부 싣는다.** 선별은 최적화지 기능이 아니다. 키가 없거나(`ELICE_*` 미설정)
모델이 죽어도 분석은 그대로 나간다 — `selection.applied=False` 와 `unavailable_reason` 으로
사실만 남긴다. 키가 없어서 못 한 경우는 `warnings` 에 띄우지 않는다(로컬 실행마다 시끄럽다).

**③ 원본은 보존하고 최종판단 입력에서만 블록을 제외한다.** `selection` 메타데이터를
원본에 남기고, `decision/agent.py`가 직렬화한 복사본에서 선택되지 않은 키를 제외한다.
배열 일부를 압축하지 않으므로 남은 `evidence.path`의 인덱스는 원본과 같다.
근거는 실제 원본에서 검증하며 `null`·빈 문자열·빈 목록·빈 객체는 거절한다.
실제 `0`·`false`는 결측값이 아니다. `source_analyses`와 저장 콜백에는 차트 원본이 유지된다.

### 모델에게 보내는 것

`data` 전체가 아니라 **요약(digest)** 을 보낸다(`_selection_digest`). 전체를 보내면 줄이려던
토큰을 선별하느라 그대로 쓰게 된다. 블록마다 "읽을 게 있는지" 판단할 최소 정보만 넣는다 —
상권 개수와 이름, 반경 단계별 값과 0 인 단계 수, 분기 수와 방향·변화율 같은 것들.

### 설정

`ELICE_API_KEY`·`ELICE_BASE_URL`·`ELICE_MODEL` 이 있으면 동작하고, 없으면 전부 싣는다.
`.env.example` 에 이미 있는 팀 공용 변수라 새로 추가할 것은 없다.

`pyproject.toml`의 `[tool.setuptools.package-data]`에
`"app.agents.floating_population" = ["prompt.md"]`가 등록되어 있다.
따라서 편집 설치뿐 아니라 배포 wheel에도 `prompt.md`가 포함된다.

## 인원수는 `daily_avg`(명/일) 하나로만 낸다

원본 데이터는 **분기 합계**다(`by_day` 합계가 총량과 같은 것으로 확인). 같은 사람의 반복
통행이 중복 집계된 **통행량**이지 사람 수가 아니다.

문제는 결정 에이전트가 세 에이전트의 `data` 를 **LLM 프롬프트에 넣어 읽힌다**는 것이다.
프롬프트에 "필드 이름, 설명, 단위와 실제 값을 함께 읽는다" 고 적혀 있고 팀 목업의 유동인구
에이전트는 `daily_average: 15,200명/일` 형태였다. 분기 합계를 그대로 실으면 **1,000배 오독**한다.

그래서 **쓸 수 있는 형태로만 내보낸다.** 아래 필드들은 "쓰지 마세요" 라고 적어야만 하는
것들이라 아예 뺐다 — 소비자가 없으면서 오독 위험만 있었다.

| 뺀 필드 | 정체 | 대신 쓰는 것 |
| --- | --- | --- |
| `population.total` | 분기 합계 | `population.daily_avg` |
| `population.male` · `female` | 분기 합계 | `population.female_ratio` |
| `population.weekday_avg` · `weekend_avg` | 분기 중 같은 요일 합계들의 평균(일평균의 13배) | `weekend_to_weekday_ratio` |
| `trend.quarters[].total` | 분기 합계 | `quarters[].daily_avg` |

**분기 합계 원값이 남아 있는 곳은 `by_age`·`by_time`·`by_day` 뿐**이고, 그 셋은
`population_raw` 로 묶여 선별 대상이다. 단위는 `population.unit` 에 적혀 있다.

규모 백분위(`benchmark.scale_percentile`)는 여전히 분기 합계로 계산한다 — 서울 기준선이 그
기준으로 측정돼 있기 때문이다. 계산에만 쓰고 `data` 에는 싣지 않는다.

## 서울시가 말하는 "상권" 은 우리가 쓰는 말과 다르다

이 데이터의 단위인 `상권` 은 **서울시가 그려놓은 분석 구역**이다. 상인들이 말하는 "역삼역
상권" 같은 생활 단위가 아니다. 서울 전체 1,650곳이 네 종류로 나뉘고 크기가 10배 이상 차이난다.

| 구분 | 개수 | 등가 반지름 중위 | 면적 중위 |
| --- | --- | --- | --- |
| 골목상권 | 1,090곳 | 157m | 77,303㎡ |
| 전통시장 | 305곳 | 85m | 22,776㎡ |
| 발달상권 | 249곳 | 218m | 149,660㎡ |
| 관광특구 | 6곳 | 448m | 629,592㎡ |

이름을 보면 성격이 드러난다 — `정독도서관` · `중앙고등학교` · `자하문터널` 이 상권 이름이다.
시설·지형을 기준점 삼아 구역을 자른 것이다. 우리가 "역삼역 상권" 하나로 부르는 곳은 이
데이터에서 다섯 조각이다.

```
역삼역                 발달상권  562,807㎡  r=423m
구역삼세무서            발달상권  291,470㎡  r=305m
역삼역 4번              골목상권   73,119㎡  r=153m   ← 지하철 출구 단위
역삼역 8번              골목상권   68,672㎡  r=148m   ← 지하철 출구 단위
역삼월드메르디앙아파트     골목상권   40,391㎡  r=113m   ← 아파트 단지 단위
```

여기서 세 가지가 따라온다.

- **`reliability.trade_area_count: 8` 은 동네 8개가 아니다.** 한 지역을 나눈 조각 8개다.
  리포트에 "주변 상권 8개" 로 쓰면 오해를 부른다 — "분석 구역 8곳" 이 맞다.
- **그래서 합산이 맞다.** 서로 경쟁하는 별개 상권이 아니라 같은 지역의 조각이므로 유동인구를
  더하는 것이 자연스럽다. 진짜 독립 상권이었다면 합산이 아니라 비교를 해야 했다.
- **발달상권이 반경 판정을 흔든 이유가 이 크기 편차다.** 등가 반지름이 400m 대인 발달상권
  하나가 판정 반경을 두 배로 늘린다(`_MAX_AREA_REACH_RATIO` 가 있는 이유).

`benchmark.scale_percentile` 도 이 구역들 사이의 순위다 — 관광특구 6곳과 아파트 단지 하나가
같은 분포에 들어 있으니 절대적 해석이 아니라 상대 위치로만 읽어야 한다.

## `scope.area` 는 `commercial_area` 와 글자까지 같아야 한다

결정 에이전트는 세 분석의 `(scope.area, scope.period)` 를 **집합에 넣어 크기로** 불일치를
판정한다(`agents/decision/agent.py`).

```python
scopes = {(item.scope.area, item.scope.period) for item in available.values()}
if len(scopes) > 1:
    limitations.append("분석 지역 또는 기준 기간이 달라 지표를 직접 비교하기 어렵습니다.")
```

완전일치 비교라 **같은 지역인데 표기만 달라도 한계가 붙는다.** 그래서 `commercial_area` 와
같은 규칙으로 만든다.

```python
area = f"{site.input_address} 반경 {radius}m"  # 양쪽 동일
```

(처음에는 강유비 문서의 목업 형식 `"서울특별시 송파구 가락동, 입력 주소 반경 500m"` 에 맞췄다가
고쳤다. 목업과 실제 구현이 다르고, 비교 대상은 실제 구현이다.)

**`period` 는 여전히 다르다** — 유동인구는 `"2026년 2분기"`, 상권은 `"2026-09-09 조회"`.
원천의 갱신 주기가 실제로 달라서 생기는 차이이므로 한계 표시가 붙는 것이 맞다. 다만 이 때문에
한계가 **항상** 붙게 되므로 표기 통일 여부는 팀 논의가 필요하다(지난 PR 리뷰포인트 5번).

⚠️ 이 에이전트는 반경을 `AnalysisTask.radius_m` 에서 읽고, `commercial_area` 는 아직 자기 설정값
(기본 500m)을 읽는다. 사용자가 500m 가 아닌 반경을 고르면 두 `scope.area` 가 달라져 한계 문구가
붙는다.

행정동은 `trade_areas[].adstrd`, 반경보다 넓게 집계한 실제 도달 거리는 `warnings` 에 있다.

## 시간대는 반드시 "시간당" 값으로 비교한다

구간 길이가 3~6시간으로 다르다. 총량을 그대로 비교하면 6시간짜리 `00_06` 이 거의 항상 1위가
된다(실데이터에서 확인된 왜곡). 그래서 `time_per_hour_share` 와 `peak_time_band` 는 시간당
값으로 계산한다. 화면에서 시간대 차트를 그릴 때도 이 값을 써야 한다.

**더 잘게는 못 나눈다.** `VwsmTrdarFlpopQq` 의 컬럼 27개 중 시간 관련은 `TMZON_00_06` ~
`TMZON_21_24` **6개가 전부**다. "시간대별 세분화" 요구는 이 데이터셋 안에서는 답이 없고,
다른 데이터셋을 붙여야 한다 — 아래 고도화 후보 ⑤ 참고.

## 유형 판정은 추정이다

원본 데이터에 직업 컬럼이 없다. "이 사람이 학생인지 직장인인지" 는 알 수 없고 연령·요일
분포에서 유추할 뿐이라 결과에 `is_inference: true` 가 붙는다.

- 4유형: 학생형 · 직장인형 · 여가상업형 · 주거생활형 (아니면 `혼합·불분명`)
- **20대는 학생 신호로 쓰지 않는다.** 대학생과 직장인을 데이터로 구분할 수 없다
  (홍대를 학생형으로 오분류하면서 배운 것)
- 임계치는 감이 아니라 **서울 전체 상권 평균 + 5%p** 로 잡았다(2026Q2 · 1,648곳 실측).
  상수와 산출 기준은 `baseline.py`·`classify.py` 주석에 있다
- 같은 입력이면 항상 같은 결과가 나온다(LLM 없음)

검증된 라벨: 길동 주거생활형 · 역삼1동 직장인형 · 서교동 여가상업형.
(상권 선택 기준을 대표 점 거리에서 면적 겹침으로 바꿔도 세 라벨 모두 유지됐다)

| 값 | 기본 | 뜻 |
| --- | --- | --- |

python -m unittest tests.test_floating_population_population   # 주거·직장·총괄·해석 문장

## 알려진 한계

- **집계 범위가 반경보다 넓다.** 상권영역 API 가 폴리곤을 주지 않아 상권 구역을 **면적
  등가원**으로 근사하고, 반경에 걸친 상권은 구역 전체를 집계한다. 그래서 실제 바깥 경계는
  반경 500m 를 넘는다(응답 `warnings` 에 이번 분석의 실제 도달 거리를 적어 둔다).
  이 판정은 양쪽으로 틀리기 쉬워서 실데이터로 상한을 잡았다 — 등가 반지름을 전부 인정하면
  843m 떨어진 `강남역` 상권이 테헤란로 분석의 37.6% 를 차지하고, 반대로 대표 점 거리만 보면
  서교동(홍대) 분석에서 `서교동(홍대)` 상권이 빠진다. 그래서 **등가 반지름을 반경의 절반까지만
  인정한다**(`geo._MAX_AREA_REACH_RATIO`). 근거 표는 `_overlapping_areas` 주석에 있다.
- **겹치는 상권이 1곳이면** 분포가 그 상권 하나에 좌우된다. `reliability.level` 이 `low` 로
  나오고 `warnings` 에도 적히므로 결정 에이전트가 무게를 낮춰야 한다.
- **유동인구 기준선은 2026Q2 실측 상수다.** 분기가 갱신되면 다시 측정해야 한다
  (`baseline.py` 의 주석 참고). 주거·직장 기준선은 응답에서 계산하므로 이 문제가 없다.
- **주거·직장 스냅샷은 사람이 갱신해야 한다.** 서울시가 값을 바꿔도 CSV 를 다시 만들기 전까지는
  옛 값이 쓰인다. 파일 분기가 유동인구 분기보다 뒤처지면 warnings 로 드러난다.
- **배포 패키지(wheel)에 CSV 를 넣으려면 `pyproject.toml` 의 package-data 에 `data/*.csv` 가
  있어야 한다.** 편집 설치(`pip install -e`)에서는 상관없다.
- **주거·직장인구 값은 2~3년 전 값이다.** 서울시가 2026년 2분기 코드로 발행하므로 그대로
  쓰지만(팀 결정 2026-09-22), "현재 인구" 로 표현하지 않는다.
- **결정 에이전트 프롬프트에 인구 블록 해석 규칙이 아직 없다.** 지금은 `description`·`unit`·
  `interpretation` 으로만 전달된다(결정 에이전트 담당과 협의 사항).

## 고도화 후보 (측정까지 해두고 남긴 것)

지금 구현으로도 동작하고 한계는 `warnings`·`reliability` 로 노출된다. 아래는 손대면 좋아지는
것이 **측정으로 확인된** 항목이다.

**① 직장인구·상주인구를 유형 판정에 넣는 것.** 블록으로는 붙였다(위 「주거인구·직장인구·인구
총괄」). 남은 것은 `classify()` 입력으로 쓰는 일이고, 아래 걸림돌 ⒜ 때문에 새 검증 기준이 먼저다.
- 걸림돌 ⒜ 이 두 데이터셋은 `tools-local/fetch_ground_truth.py` 가 **검증 정답으로 쓰고 있다.**
  판정 입력으로 넣으면 정답과 입력이 같아져 검증이 무의미해지므로 새 검증 기준이 필요하다.
- 걸림돌 ⒝ 유동인구는 통신사 기반 **통행량**, 나머지 둘은 **사람 수**다. 판정 입력으로 섞을 때도
  더하지 않고 비율로만 써야 한다.

**② 시간대를 유형 판정에 넣는 것.** 지금 `classify()` 는 연령과 주말/주중만 본다. 정답 대비로
재보니 **낮(11~17시) 시간당 비중이 직장인형을 30·40대보다 잘 예측한다(F1 0.83 vs 0.68).**
임계치를 정답 데이터로 다시 잡아야 한다(`tools-local/fetch_ground_truth.py` 로 정답 수집).

**③ 반경 규칙을 혼합으로.** 반경 고정은 지역 밀도에 따라 표본이 출렁인다(실측: 명동 10곳 ·
역삼1동 8곳 · 오금로404 3곳 · 평창동 2곳 · 개화동 0곳). "가까운 N곳" 으로 바꾸면 표본은
안정되지만 평창동에서 5곳을 채우려면 1,206m, 10곳이면 2,527m 까지 가야 해 지역 대표성을
잃는다. 반경 우선 + 3곳 미만이면 1,000m 로 한 번 확장 + 확장 사실을 밝히는 쪽이 맞아 보인다.
단 `scope.area` 의 반경이 요청마다 달라져 결정 에이전트의 `(area, period)` 일치 검사에 영향이
간다.

**④ 좌표 변환(`geo.py`)의 공용화.** 개폐업 에이전트가 쓸 `VwsmTrdarStorQq`(점포-상권,
개업률 `OPBIZ_RT`·폐업률 `CLSBIZ_RT`·프랜차이즈 점포수 `FRC_STOR_CO` 포함)도 **같은 상권
단위라 반경 검색이 없다.** 같은 변환·선택 로직이 필요하므로 공용 위치로 빼면 두 에이전트가
함께 쓴다.

**⑤ 시간대 세분화 — 생활인구 데이터셋을 붙여야 한다.** 지금 원자료는 6구간이 전부라 이
데이터셋 안에서는 더 쪼갤 수 없다. 같은 API 키로 **`SPOP_LOCAL_RESD_DONG`**(행정동단위
서울생활인구 내국인, 630,988행)이 열리는 것을 확인했다:

```
STDR_DE_ID  = 20260731   ← 일별
TMZON_PD_SE = '00'       ← 24시간, 시간당
연령        = 0~9, 10~14, 15~19, 20~24, 25~29 ... 70~74  ← 5세 단위 × 성별
```

**24시간 × 일별 × 5세 단위**라 세분화 요구를 실제로 충족하는 유일한 길이다. 걸림돌 셋:
- ⒜ **행정동 단위이고 좌표가 없다**(이름 매칭만). 반경 분석과 지역 단위가 달라져
  `scope.area` 가 흔들린다.
- ⒝ **생활인구 ≠ 유동인구다.** 그 시점 그 지역에 있는 사람 수의 추계(실수값)이지 통행량이
  아니다. 고도화 ① 과 같은 문제라 `data` 안에서 단위를 분리한 별도 블록이어야 한다.
- ⒞ 일별이라 **어느 날짜(또는 어느 기간의 평균)를 쓸지** 정해야 한다. 분기 단위인 지금
  자료와 기간이 안 맞아 `scope.period` 불일치가 하나 더 생긴다.

팀 합의가 필요한 사안이라 코드에는 넣지 않았다.
