# Git 워크플로

## 브랜치

```
main      멘토 승인을 받은 상태. 주간 develop → main PR로만 들어온다
develop   기본 브랜치. 팀의 현재 상태이자 운영 서버에 배포되는 브랜치
feature/* 기능 작업.  feature/commercial-area-async
fix/*     버그 수정
refactor/* 리뷰 반영·정리
docs/*    문서만 바뀔 때
```

**develop에 들어간 커밋은 곧 운영 배포입니다.** develop에 push되면 `deploy.yml`이 백엔드 검사(ruff · mypy · unittest)를
다시 돌리고, 통과해야만 EC2에 무중단으로 배포합니다. 검사가 실패하면 배포하지 않고 지금 버전이 계속 서비스합니다.

**작업 브랜치는 develop에서 따고 develop으로 돌아옵니다.** `main`에 직접 push하지 않습니다.

```bash
git switch develop && git pull
git switch -c feature/무엇을-하는지
```

## 커밋

`type: 무엇을 했는지` 한 줄. 한국어로 씁니다.

| type | 쓸 때 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조만 바꿈 |
| `docs` | 문서 |
| `test` | 시험 추가·수정 |
| `chore` | 설정·의존성 |

```
feat: 상권 에이전트 비동기 전환과 페이지 병렬 조회
fix: 자치구 코드가 없을 때 분석이 멈추던 문제
docs: 백엔드 README에 데이터 흐름 추가
```

**한 커밋은 한 가지만 합니다.** 포맷 정리와 기능 추가를 같은 커밋에 섞지 않습니다.
리뷰어가 "이건 왜 바뀌었지"를 묻지 않아도 되게 만드는 것이 목적입니다.

## PR

### 팀 내부 PR — `작업 브랜치 → develop`

- 기능 추가 · 구조 변경 · 화면 변경은 PR로 올립니다. 본문은 PR 템플릿(이번에 한 일 · 봐주셨으면 하는 곳 · 고민한 점)을 채웁니다.
- CI(`ci.yml`)가 통과하면 작성자가 머지합니다.
- 팀원 리뷰는 필수가 아닙니다. 1인 1역으로 파트를 나눠 일하고, 한 주 변경 전체는 아래 멘토 리뷰에서 함께 봅니다.
  같은 API나 화면을 건드리는 사람이 있으면 리뷰어로 지정해 서로 무엇을 바꾸는지 알게 합니다.
- 리뷰가 하루 넘게 막히면 그냥 머지합니다. **리뷰가 병목이 되면 리뷰를 안 하는 것보다 나쁩니다.**

#### PR 없이 develop에 바로 올려도 되는 경우

- 문서만 바꿀 때
- 멘토 리뷰 지적을 반영할 때 — 열려 있는 `develop → main` PR에 커밋이 붙어 멘토가 2차 리뷰에서 다시 봅니다
- 운영 장애를 급히 고칠 때

어떤 경우든 push 전에 [AGENTS.md](../AGENTS.md)의 "작업 전에 돌리는 것"을 로컬에서 돌립니다. develop은 곧 운영 배포입니다.

### 멘토 리뷰 PR — `develop → main` (주 1회)

1. 매주 화요일쯤 팀장이 그 주 작업을 `develop → main` PR로 올립니다.
   **base가 `main`인지 확인합니다.** GitHub이 `develop`을 기본으로 채워 두는데, `main`이 아니면 멘토가 자동 지정되지 않습니다.
2. PR 템플릿의 **"리뷰에서 봐주셨으면 하는 곳"** 을 반드시 채우고, 질문은 **2~3개로 좁힙니다.**
   "전체 봐주세요"보다 "이 방식이 맞는지 모르겠습니다"가 훨씬 나은 리뷰를 받습니다.
3. 멘토가 1차 리뷰를 남기면 **지적마다 답글을 답니다.** 고쳤으면 어디를 어떻게(커밋 · PR 번호),
   고치지 않기로 했으면 그 이유를 적습니다.
4. 고친 커밋을 develop에 올리면 같은 PR에 붙습니다. 멘토가 2차 리뷰에서 승인하면 main에 머지합니다.

9/9부터 11/4까지 8번(#7 · #17 · #26 · #32 · #35 · #47 · #57 · #70) 이 순서로 리뷰받았고,
8번 모두 변경 요청 → 답글 · 수정 → 승인으로 닫았습니다. 회차별 지적과 반영 내용은 노션 「코드 리뷰 기록 — 주요 PR」에 있습니다.

## 충돌이 났을 때

```bash
git switch develop && git pull
git switch feature/내-브랜치
git merge develop        # rebase 대신 merge를 씁니다. 이력이 남는 편이 추적하기 쉽습니다
```

`package-lock.json`이 충돌하면 develop 쪽을 받고 `npm install`을 다시 돌립니다.

## 리뷰 자동화 — 건드리지 않기

`.github/workflows/assign-mentor.yml` · `notify-discord.yml` · `convention-check.yml` · `.github/CODEOWNERS`
운영진 소유입니다. 팀 CI(`ci.yml`)를 포함해 **새 워크플로를 추가하는 것은 자유**지만
위 4개는 고치지 않습니다.
