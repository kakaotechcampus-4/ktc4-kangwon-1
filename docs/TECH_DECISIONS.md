# 채움 백엔드 설계 결정 기록 (ADR)

빈 상가 주소 하나를 받아 **임대인이 읽을 수 있는 업종 추천 문장과 그 근거**를 돌려주는 시스템의 주요 설계 결정을 기록합니다.
각 항목은 **맥락 → 결정 → 대안과 선택 이유 → 대가(트레이드오프) → 코드 위치 → 검증** 순서로 씁니다.
수치는 모두 저장소의 테스트·진행 기록(`docs/mvp20-progress.md`)에서 확인한 값이며, 단회 측정은 단회라고 밝힙니다.

## 한 장 요약 — 설계 원칙

| 원칙 | 구현 |
| --- | --- |
| **LLM은 선택지가 둘 이상인 곳에만** | 판단(최종판단) 1곳만 LLM. 실행 순서·분석 지표·라벨은 결정론적 코드 |
| **흐름은 상태 기계로, 판단은 모델로** | LangGraph 고정 엣지 + 판단 후 조건부 분기. 모든 루프는 횟수 상한 |
| **모델 출력은 검증 전까지 신뢰하지 않는다** | pydantic 계약 + 근거 경로 인덱싱·7가지 검증 + 자동 치환 금지 |
| **실패는 가장 작은 단위에서 끝낸다** | 분석별 타임아웃·오류 격리, 계약 오류만 요청 경계까지 전파 |
| **측정한 뒤 복잡도를 더한다** | 에이전트형 오케스트레이터는 실측 결과로 미도입 결정 |
| **숨기지 않는다** | 단위·범위·표본 한계를 결과(`limitations`, `rate_basis`)에 기록 |

## ADR-01. 실행 엔진으로 LangGraph를 쓴다

**맥락.** 기본 흐름(주소 → 3개 분석 → 판단) 뒤에 판단 결과에 따라 **보완 재조회 / 지도 조회 / 임대인 질문** 세 갈래가 붙고, 보완·지도는 다시 판단으로 돌아와야 합니다. 분기와 복귀가 섞인 흐름을 `if/while`로 쓰면 상태 플래그가 함수 곳곳에 흩어지고, "지도 뒤 보완 뒤 질문" 같은 조합을 추적하기 어렵습니다.

**결정.** `StateGraph`로 노드 7개(`prepare_address`, `run_analyses`, `evaluate_decision`, `execute_supplement`, `execute_map`, `ask_user` + START/END)와 엣지를 **선언적으로** 정의합니다. 판단 이후에만 `add_conditional_edges`로 분기합니다.

**대안과 선택 이유.**

| 대안 | 기각 이유 |
| --- | --- |
| 직접 작성한 while 루프 | 분기가 늘수록 중첩·플래그가 증가. 가능한 전이를 한눈에 볼 수 없음 |
| ReAct형 에이전트(LLM이 매 단계 도구 선택) | 흐름이 모델 출력에 따라 비결정적. 실제로는 선택지가 하나뿐인 단계에서도 호출 비용·실패 지점 발생 (ADR-02) |
| **LangGraph StateGraph** ✅ | 전이가 코드로 명시되고, 노드가 순수한 `state → partial state` 함수라 단위 테스트가 쉬움. `recursion_limit=32` 안전망 제공 |

**설계 포인트.**
- **상태에는 요청 데이터만** 둡니다(`GraphState`). 실행 함수·키·클라이언트는 클로저로 주입해 요청 간 공유 상태가 없고, 동시 요청이 섞이지 않습니다.
- **LangGraph 체크포인터는 쓰지 않습니다.** 질문 대기 후 재개는 SQLite에 **도메인 스냅샷**(`question_sessions`: 작업·질문·보완 문맥·분석 차수)으로 저장합니다. 프레임워크 직렬화 형식에 묶이지 않고, 스키마 버전 관리·감사가 가능하며, 분석 결과를 두 곳에 중복 저장하지 않습니다.
- `tracing_context(enabled=False)` — 주소·분석 자료가 외부 추적 서비스로 나가지 않게 기본 차단합니다.

**대가.** 프레임워크 의존성이 생깁니다. 대신 사용 범위를 `StateGraph` 핵심 API로 한정해 교체 비용을 낮췄습니다.

**코드.** `backend/app/agents/orchestration/graph.py` — `run_graph`, `GraphState`, `RunHooks`

## ADR-02. 오케스트레이터 LLM을 제거하고, 에이전트형 확장은 측정으로 보류했다

**맥락.** 초기 구조는 오케스트레이터 LLM이 매 단계 "다음 도구"를 골랐습니다. 그러나 코드가 이미 허용 순서를 강제하고 있어(`expected` 도구 외에는 에러 관찰 반환) **LLM이 고를 수 있는 정답은 늘 하나**였습니다. 분석 1회당 모델 호출 3회가 판단 없이 소비되고, 거절·다중 호출 시 요청이 실패하는 새로운 실패 모드가 생겼습니다.

**결정.** 첫 실행을 `prepare_address → run_analyses → evaluate_decision` **고정 엣지**로 바꾸고, 오케스트레이터 모델·프롬프트·도구 정의·호환 인자를 제거했습니다. 판단 이후의 보완·지도·질문 분기는 유지합니다.

**측정 (실제 API·LLM, 반경 500m, 주소 3곳, 각 단회).**

| 주소 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 송파구 오금로 404 | 37.83초 | 28.93초 |
| 강남구 테헤란로 123 | 50.90초 | 35.66초 |
| 성동구 아차산로 83 | 40.08초 | 29.97초 |

- 오케스트레이터 LLM 호출 **3회 → 0회/주소**, 최종판단 LLM은 전후 1회로 동일.
- 중앙값 40.08초 → 29.97초. 단회 관측이라 네트워크·캐시·모델 출력량 영향을 분리하지 않았으며, 개선분 전부를 코드 효과로 단정하지 않습니다.

**에이전트형 오케스트레이터(7단계)를 도입하지 않은 이유.** 설계안은 "최종판단이 부족 정보 목록을 내면 오케스트레이터 LLM이 동적 도구 목록·예산 안에서 선택"이었습니다. 같은 3곳 실측에서 보완·지도·질문 요청 비율이 **0/3**이었으므로, 추가 LLM 계층의 비용·비결정성을 정당화할 근거가 없었습니다. 필요한 평가 사례가 쌓이면 같은 방식으로 재측정해 결정합니다. **"멋있어 보이는 에이전트"보다 측정 가능한 이득을 기준으로** 복잡도를 추가합니다.

**코드.** `graph.py` 엣지 정의, 진행 기록 `docs/mvp20-progress.md`

## ADR-03. 판단은 LLM, 근거 경로의 탐색과 검증은 코드

**맥락.** 최종판단은 추천마다 근거 `evidence.path`(분석 결과 안의 위치)를 붙입니다. 업종 **코드는 고정**이지만 결과 **배열 위치는 실행마다 달라집니다**(들어온 업종 수·순서에 따라). 모델이 배열 번호를 직접 쓰게 하면 없는 경로나 **다른 업종의 자료**를 인용할 수 있습니다. 임대인은 이를 검증할 수단이 없습니다.

**결정 — "생성" 대신 "선택"으로 문제를 바꾼다.**
1. `index_paths(data)` — 분석 데이터를 깊이 우선 탐색해 **값이 있는 모든 JSON Pointer 경로**(RFC 6901, `~0`/`~1` 이스케이프)를 만들고, 각 경로의 **소유 업종**을 가장 가까운 업종 식별 조상에서 전파합니다.
   - 서로 다른 업종이 섞인 상위 객체, `data_available=False`, `confidence="none"`, `score_available=False`, `citable=false` 하위 트리는 **인용 불가**.
   - 차단된 자식을 포함한 **부모 경로로 우회 인용하는 것도 차단**, 반면 실제 값 `0`은 유지(0은 "없음"이 아니라 관측값).
2. `industry_catalog()` — 위 결과를 `{agent_id, industry_code, industry_name, paths}`로 묶어 **첫 모델 입력부터** 제공합니다. 모델은 경로를 만들지 않고 목록에서 고릅니다.
3. `_validate_evidence()` — 출처 사용 가능, 경로 형식, 경로 존재, 빈 값, 인용 가능, **추천 업종 = 근거 업종**을 순서대로 검사하고, 업종 자체도 `unknown_industry · major_mismatch · duplicate_industry`로 검사합니다.

**교정 루프 설계.**
- 근거 오류 시 같은 업종(없으면 공통) 경로에서 `difflib.get_close_matches(n=8, cutoff=0.2)`로 **후보만 제시**합니다. 잘못된 업종 코드·코드와 명칭 불일치도 교정 대상입니다. **최초 생성 1회 + 교정 최대 1회**이며, 교정 호출에서는 보완·지도·질문 요청을 금지합니다.
- **코드가 경로를 자동 치환하지 않습니다.** 치환하면 모델이 쓴 "이유 문장"과 근거 숫자가 어긋난 채 저장될 수 있기 때문입니다. 끝내 실패하면 정상 결과로 저장하지 않고 `decision_failures`에 잘못된 경로·후보를 진단으로 남깁니다.

**왜 이 방식인가.** 모델의 자유도를 "해석과 선택"으로 좁히면 환각이 들어갈 공간 자체가 줄고, 남은 오류는 결정론적 검증으로 잡힙니다. 규칙(`citable`)은 **인덱서 한 곳**에서만 강제하므로 에이전트가 늘어도 정책이 하나입니다.

**코드.** `backend/app/agents/decision/evidence.py`, `decision/agent.py` (`_validate_evidence`, `_correction_detail`)

## ADR-04. 비동기 I/O와 실패 격리

**맥락.** 분석 1회에 공공 API 요청이 100회를 넘습니다. 동기 호출 하나가 FastAPI 이벤트 루프를 멈추면 **다른 사용자의 요청까지** 대기합니다. 실제로 상권 캐시(35MB JSON)를 async 함수 안에서 동기로 읽던 경로가 있었습니다.

**결정.**
- 외부 호출은 `httpx.AsyncClient`만 사용하고, 세 분석은 `asyncio.gather`로 **동시 실행**, 분석마다 `asyncio.timeout`을 둡니다.
- 피할 수 없는 블로킹 작업(대용량 캐시 JSON, SHP 파싱, SQLite, 개폐업 집계·pandas 채점·결과 변환)은 `asyncio.to_thread`로 격리합니다. 개폐업의 기존 `urllib` 동기 경로는 공용 비동기 클라이언트(`app/seoul.py`)로 교체했습니다.
- 개폐업 분기는 요청당 최대 4개씩 병렬 조회하고 원래 분기 순서로 합칩니다. 조회 실패·취소 시 `TaskGroup`이 나머지 조회를 정리합니다. 속도가 분기 수만큼 개선된다는 보장은 없습니다.
- 캐시는 실제 사용하는 **14개 필드만 저장**해 직렬화 비용 자체를 줄이고, 기존 전체 필드 캐시도 읽도록 하위 호환을 유지했습니다.

**실패 격리 규칙.**
- 외부 API의 일반 실패 → 해당 분석만 `status="error"`/`"partial"` + 오류 코드(`UPSTREAM_ERROR`·`UPSTREAM_TIMEOUT`·`CONFIG_ERROR`·`BAD_RESPONSE`). 나머지 분석과 판단은 계속.
- **계약 위반(`ValidationError`)만** 요청 경계까지 전파해 failed로 저장 — 잘못된 데이터를 "부분 결과"로 숨기지 않기 위해서입니다.
- 오류 메시지에는 키·외부 URL·원문 예외를 넣지 않습니다.
- 저장 메시지는 판정 계약 오류·취소·시간 초과·저장 실패를 구분합니다. 판단 재시도 실패 코드는 기존대로 유지해 다음 재시도를 막지 않습니다.
- `run_graph()` 직접 호출도 주소·요청 ID·에이전트 구성·콜백을 외부 호출 전에 검증합니다. 질문을 허용하면서 질문 저장 콜백이 없는 구성은 즉시 거절합니다.

**동시 요청 상한 — 이벤트 루프 단위 세마포어.** 상권 API 동시 요청 한도를 `WeakKeyDictionary[event_loop → Semaphore]`로 관리합니다. 한 워커 안의 모든 요청이 **같은 한도를 공유**하고(두 클라이언트 동시 요청이 상한을 넘던 문제를 재현 후 수정), 루프가 사라지면 세마포어도 GC됩니다. 대기·실패·취소 시 슬롯을 반환합니다.

페이지 수만큼 작업을 미리 만들지 않고 제한된 worker만 페이지를 가져옵니다. 한 사용자의 120페이지가 공유 슬롯 대기열을 한꺼번에 채우지 않도록 합니다.

**대가.** 사용자별 엄격한 공정성 보장이나 다중 워커를 합친 전역 쿼터는 아닙니다. 부하가 늘면 요청별 스케줄링을, 다중 인스턴스 배포 시에는 외부 쿼터 제어를 별도로 검토해야 합니다.

**코드.** `orchestration/workflow.py` `run_agents`, `app/seoul.py`, `commercial_area/client.py` `_request_limit`

## ADR-05. 취소에 안전한 저장 — `_settle`

**맥락.** `asyncio.to_thread`로 넘긴 DB 쓰기는 **중간에 강제 종료할 수 없습니다.** 요청이 취소·타임아웃될 때 바로 `CancelledError`를 올리면, 스레드는 커밋을 끝냈는데 호출자는 실패로 처리하는 **상태 불일치**가 생깁니다.

**결정.** `_settle()`이 `asyncio.shield`로 쓰기 작업의 **결말을 끝까지 확인한 뒤** 취소를 전파합니다. 또한 `create_request` INSERT에 성공한 호출(`owned`)만 그 요청의 실패 상태를 기록할 수 있어, 경쟁하는 두 호출이 서로의 상태를 덮어쓰지 않습니다.

**코드.** `backend/app/services/analysis.py` `_settle`, `_failure_code`, `_record_failure`

## ADR-06. 저장 — SQLite WAL, 멱등 재개, 업종표 버전 고정

**결정과 근거.**
- **SQLite + WAL**(`journal_mode=WAL`, `foreign_keys=ON`, `timeout=5`) — MVP 단계에서 운영 부담 없이 읽기·쓰기 동시성을 확보합니다. 테이블 7개가 `request_id`로 묶여 요청·분석 이력·보완 이벤트·지도 관측·질문·판단 이력·실패 진단을 **감사 가능한 이력**으로 남깁니다.
- **질문 재개는 원자적 선점(claim)** — `waiting_for_input → running` 상태 전이를 한 트랜잭션에서 수행해 같은 답변의 중복 재개를 409로 막고, **같은 답을 완료 후 재전송하면 저장된 결과를 반환**합니다(멱등).
- **재개는 전체 재분석이 아닙니다.** `load_resume_context()`가 저장된 분석·채택된 보완·지도 관측·답변을 복원해 `decision.evaluate()`만 호출합니다. 외부 API 100회+를 다시 부르지 않습니다. 질문 재개와 판단 재시도가 같은 복원 로직을 공유합니다.
- **`catalog_version`을 요청마다 저장** — 업종표가 바뀐 뒤 옛 요청을 재개하면 옛 코드로 만든 분석이 새 검증에 걸립니다. 버전이 다르거나 미상이면 **상태를 바꾸기 전에** 명확히 거절합니다. 과거 결과 조회는 유지합니다.

**대가.** 다중 인스턴스 쓰기에는 부적합합니다(PostgreSQL 이전이 다음 단계). 동시 WAL 초기화 시 잠금 경합이 테스트에서 간헐 재현되어 후속 점검 항목으로 기록했습니다.

**코드.** `app/db/connection.py`, `app/db/repository.py` (`claim_question_resume`, `load_resume_context`), `app/db/schema.sql`

## ADR-07. 공통 계약은 한 파일, 하위 호환으로 진화

**결정.** 에이전트 간 입출력은 `backend/app/schemas.py`(pydantic strict)가 **유일한 기준**입니다. 각 에이전트가 자유롭게 정하는 곳은 `AgentAnalysis.data` 안쪽뿐이고, 나머지 변경은 PR 합의가 필요합니다.

**계약 진화 사례 — `Category.code`.** 결과에 업종 코드(`I212`)를 추가하면서 `model_validator(mode="before")`로:
- 코드만 오면 공식 대분류·중분류명을 채우고, 코드와 이름이 불일치하면 거절
- 이름만 있는 **과거 저장 결과도 읽음**(역조회) → 기존 `major`·`middle` 소비자(프론트)를 깨지 않는 **추가형 변경**

모델에는 코드만 선택하도록 안내합니다. 그래도 모르는 코드나 코드·이름 불일치가 오면 모델 출력 경계에서 `invalid_category`로 분류해 교정 1회를 허용합니다. 재실패는 `DECISION_CONTRACT_INVALID`이며, API·저장 계약의 엄격한 검증은 완화하지 않습니다. 잘못된 원본 출력은 교정 입력에만 사용하고 공개 진단에는 넣지 않습니다.

## ADR-08. 75개 업종표는 DB가 아니라 "버전 관리되는 코드"

**결정.** 원본은 `industries/data/*.csv` → 생성 스크립트가 `catalog.py`(`Final` 상수 + `CATALOG_VERSION` 해시)를 생성 → 동기화 테스트가 CSV와 생성물 불일치를 CI에서 차단합니다.

**DB로 옮기지 않은 이유.** 거의 바뀌지 않는 기준 어휘는 코드와 함께 배포될 때 가장 안전합니다. 변경이 **PR diff로 리뷰**되고, 런타임 I/O가 0이며, mypy가 상수를 검사합니다. 상권 에이전트가 CSV를 별도로 파싱하던 경로와, 소비처가 없던 JSON 생성물은 제거해 **원본을 하나로** 줄였습니다.

## ADR-09. 분석 에이전트의 LLM을 결정론적 규칙으로 대체

**맥락.** 세 분석 에이전트가 라벨 붙이기·요약·표시 항목 선별에 LLM을 쓰고 있었습니다. 개폐업은 배치 약 7회를 **순차 호출**했고, 한 배치만 실패해도 **이미 계산한 75개 업종 점수 전체를 버렸습니다.** 최종 문장은 어차피 최종판단이 씁니다.

**결정.**
- 개폐업 유형: 기간 내 **개업·폐업 건수 비교**로 `개업 우위 / 폐업 우위 / 개폐업 균형`. 새 임계값을 발명하지 않기 위한 선택입니다.
- 상권 요약: 조회 반경·점포 수로 템플릿 문장 생성.
- 인구 선별: 비어 있지 않은 자료 + 2개 분기 이상 추세 유지 규칙.
- 의도된 자료 선별은 `selection` 메타데이터에만 남깁니다. 실제 자료 부족·범위 차이·선별 실패 경고와 구분하며, 내부 처리 때문에 자동으로 `partial`이 되지 않게 합니다. 선택 상권의 이름이 누락되면 코드를 표시하고 경고하되 관측값은 보존합니다.
- 상권코드 누락·공백과 비유한 좌표·인구 값은 API·CSV 파싱에서 거절합니다. 이름 누락과 달리 집계 식별자·수치 오류는 외부 자료 실패로 처리하고, 다른 분석 결과는 보존합니다. 정상 관측값 0은 허용합니다.

**효과.** 분석 경로 LLM 호출 0회 → 지연·비용·실패 지점 제거, **같은 입력 → 같은 출력**(재현성)으로 회귀 테스트 가능. 남은 LLM은 판단 1곳과 지도 분류 매핑뿐입니다.

## ADR-10. 지도 분류 매핑 캐시 — 내용 주소 방식

**맥락.** 카카오 장소 분류(예: `음식점 > 카페 > 커피전문점`)를 75개 업종으로 매핑하는 데 LLM을 쓰며, 같은 분류를 관측마다 다시 물었습니다.

**결정.**
- 캐시 키 = **분류 내용 + 업종표 버전 + 프롬프트 + 모델 + endpoint의 해시.** 어느 하나라도 바뀌면 자동으로 새 키가 되어 **명시적 무효화가 필요 없습니다.**
- 모델이 `mapped`로 확정한 결과만 저장(미확정·오류는 캐시하지 않음 — 부정 결과 고착 방지), TTL 7일, SQLite I/O는 스레드 격리, 캐시 손상·실패 시 모델 경로로 폴백.
- 캐시 일부 적중 후 새 분류 매핑이 실패하면 기존 매핑·원본 장소를 보존하고 `partial`로 반환합니다. 업종 미확정 장소는 업종별 건수에서 제외하고 제외 건수를 경고로 표시합니다.
- 키워드 검색 부풀림("커피"가 상호에만 있어도 집계)은 대응이 확실한 업종에만 카카오 분류 필터(카페 CE7, 음식점 FD6)를 적용해 줄였습니다. 불확실한 업종에 추정 매핑을 넣지 않았습니다.

**대가.** 사람이 검수한 정답표가 아닙니다(의미 오매핑 가능성 → 수동 검수는 별도 과제). 동시 최초 조회 시 중복 호출이 생길 수 있으나 요청 병합(single-flight)은 복잡도 대비 이득이 작아 보류했습니다.

## ADR-11. 상권 경계(SHP) 파싱 캐시

**결정.** 3.6MB SHP 파싱 결과를 `lru_cache(maxsize=4)`로 캐시하되, 키에 **구성 파일 4개의 `(st_mtime_ns, st_size)` 시그니처**를 넣어 파일이 교체되면 자동으로 다시 읽습니다. 피처·좌표는 중첩 튜플, 속성은 `MappingProxyType`으로 반환합니다. 요청마다 깊은 복사하지 않으면서 다른 요청의 자료를 변경할 수 없도록 합니다. 좌표 포함 판정(짝홀 규칙)과 경계 위 점 처리는 기존 로직을 유지합니다.

**코드.** `business_lifecycle/area_resolver.py`

## ADR-12. 통계 지표 — 임대인에게 틀리게 읽히지 않는 숫자

**폐업률 = 점포 가중 분기 평균.** `Σ(4개 분기 폐업 수) ÷ Σ(분기별 점포 수)`. 분기마다 비율을 구해 평균하는 것보다 **소형 업종의 분기별 변동에 강건**합니다. 이 값을 "1년 폐업률"로 표기하던 오류(연간 대비 약 1/4로 보임)를 발견해 **이름과 단위를 바로잡고**, 결과에 `scoring_method.rate_basis`(단위·분모·기간·비연율화)를 명시했습니다. 연간 값으로 재계산하지 않은 이유: 업종 점수는 **업종 간 순위**라 기준을 바꿔도 순위가 같고, 새 숫자를 발명해 혼란을 늘리지 않기 위해서입니다.

**입지계수(LQ) 소표본 차단.** `LQ = 반경 내 업종 비중 ÷ 기준 반경 업종 비중`. 점포 수가 작으면 비율 분산이 폭증하므로(1곳 차이로 LQ가 배로 변동), 기존 기준 `min_count_for_specialization = 5` 미만은 수치를 보존하되 **근거 인용을 차단**합니다. 0개 업종은 순위 목록에서 빼고 전체 집계에는 남깁니다("없다 = 기회"라는 잘못된 해석 방지).

**결측은 0이 아니다.** 빠진 분기는 NaN으로 전파하고 0으로 채우지 않습니다. 채점 가능 업종이 1개뿐이면 백분위 점수를 **보류**하고 `confidence="low"`로 표시합니다(비교 대상 없는 100점 방지). 이때 요약도 "0개 업종 비교"가 아니라 비교 자료 부족으로 점수를 보류했다고 설명합니다.

**공간 범위를 섞지 않는다.** 개폐업은 공식 상권 폴리곤, 인구·상권은 요청 반경 기준입니다. 같은 집합으로 강제하지 않고, 범위 차이를 결과 한계로 기록합니다.

## ADR-13. 보완(supplement) 결과는 "증명될 때만" 채택 — fail-closed

**결정.** 최종판단이 요청한 보완은 **판단에 실제 제시한 작업만**, 실행 직전 `eligible()`을 다시 확인한 뒤, 최대 1라운드 실행합니다. 결과 채택은 두 겹입니다.
1. 오케스트레이터: 원본 필드가 그대로 보존되고 **추가만** 있는지 검사
2. 도메인 `accept()`: 개폐업은 기간 개·폐업 합계, 최근 4분기 건수, 최신·평균 점포 수, 분기 폐업률(같은 반올림)을 재계산해 원본과 비교

비교할 원본 합계가 없으면 **검증 불가로 거절**합니다(fail-closed). 결측을 0으로 바꾸지 않습니다.

## ADR-14. 결과 상태 모델 — "실행 상태"와 "결과 품질"의 분리

- 실행 상태: `pending · running · waiting_for_input · completed · failed` (DB 제약으로 강제)
- 결과 품질: `ok · partial · no_data`
- 결과가 `partial`이어도 정상 반환이면 실행은 `completed`입니다. 프론트는 둘을 섞지 않고, `partial·no_data`일 때 `limitations`를 반드시 노출합니다.

## 검증 방식

- **실패 재현 우선(TDD).** 모든 버그 수정은 실패하는 테스트로 문제를 재현한 뒤 수정했습니다(예: 분기 평균 단위 누락, 캐시 동기 실행, 재시도 중 취소가 다음 재시도를 막는 회귀).
- 2026-09-29 커밋 직전 원자료 검증 보강 후: 백엔드 테스트 **486개**, 검증 도구 **30개** 통과, Ruff·포맷(백엔드 158개·검증 도구 8개 파일)·mypy(77개 소스) 통과, 업종표 CSV–catalog 동기화 검사 통과.
- 단계마다 **독립 읽기 전용 리뷰**를 거쳤고, 인용 차단 우회(부모 경로·배열·`/citable` 자체 인용 등)를 직접 실행해 확인했습니다.
- 대역(mock) 실행으로 외부 호출 없이 전체 흐름·보완 채택·지도·질문·재개를 회귀 검사합니다.
- 실제 주소 1회 재실행: `9608ebafc750425fbefa185c8f7742b4`, 오금로 404·500m, 33.79초. 분석 3개·판단 1개·DB completed를 확인했습니다. 자료·범위 한계가 남아 결과는 partial이며, 추천 4개·비추천 5개입니다. 최종판단 교정·보완·지도·질문은 이 실행에서 발생하지 않았습니다. 캐시가 유지된 단회 실행이므로 성능 보장이나 추천 품질 평가로 해석하지 않습니다.

## 예상 질문

- **왜 LangGraph인데 LLM이 순서를 고르지 않나?** LangGraph는 "LLM 에이전트 프레임워크"가 아니라 여기서는 **명시적 상태 기계**로 씁니다. 선택지가 하나뿐인 곳에 LLM을 두지 않는 것이 비용·신뢰성 면에서 맞고, 판단 뒤 분기에서만 모델 출력이 흐름을 결정합니다.
- **환각은 어떻게 막나?** 경로를 생성이 아닌 선택 문제로 바꾸고(ADR-03), 선택 결과를 결정론적으로 재검증하며, 실패 시 저장하지 않습니다.
- **체크포인터 없이 어떻게 재개하나?** 재개에 필요한 것은 그래프 내부 상태가 아니라 도메인 자료(분석·보완·지도·답변)입니다. 이를 SQLite에 스키마로 저장해 버전 검증과 감사를 함께 얻었습니다.
- **LLM을 줄여 품질이 떨어지지 않나?** 줄인 곳은 규칙이 명확한 라벨·요약·선별입니다. 종합 판단은 그대로 LLM이며, 재현성이 생겨 품질 회귀를 테스트로 잡을 수 있게 됐습니다.
