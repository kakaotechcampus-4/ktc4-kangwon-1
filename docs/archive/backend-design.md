# 백엔드 책임·계약·운영 구조 설계

작성: 2026-10-03 · 기준: `perf/specialist-inputs`, `f7aebe6` · 상태: A부 구현·오프라인 검증 완료

이 문서는 설계 범위와 경계를 정한다. 이후 사용자 승인으로 A부를 구현했고 진행 기록과 측정 결과를
추가했다. 공통 계약 변경 합의를 대신하지 않는다. 완료 근거는
[진행 기록](backend-refactoring-progress.md)에 있으며 B부는 구현하지 않았다.

## 1. 목적과 범위

목적은 분석 동작을 유지하면서 내부 계약과 책임을 명확히 하고, 실제 오류를 고친 뒤 운영 확장이 가능한 경계를 만드는 것이다. 패턴 수나 파일 수를 늘리는 것이 목표가 아니다.

- 대상: `backend/app`, 관련 백엔드 테스트·실행 스크립트·문서.
- 프론트엔드, 로컬 `validation_tool`, 보호된 GitHub 자동화는 변경하지 않는다.
- 기존 HTTP 응답·상태 코드·오류 문구·공개 함수 시그니처·DB 형식은 A부에서 유지한다. 확인된 버그 수정은 별도 회귀 테스트로 고정한다.
- `schemas.py` 계약 변경, 인증, SSE, 외부 큐, 서버형 DB는 B부이며 팀 합의와 별도 실행 승인이 필요하다.
- 기존 `refactor-plan.md` C1~C15와 `efficiency-plan.md` P1~P7에서 완료된 작업은 다시 수행하지 않는다.
- `report-plan.md`는 사용자 작성 구상이다. 수정하지 않으며 구조화 수치는 그 문서의 Figure 설계와 함께 결정한다.

구현 계획: [backend-refactoring 계획](superpowers/plans/2026-10-03-backend-refactoring.md).

## 3. 선택한 구조

대안은 세 가지다. 기존 함수 모듈을 그대로 정리하면 비용은 작지만 저장소·상태 계약이 약한 부분이 남는다. 전체를 범용 서비스·저장소 프레임워크로 바꾸면 변경량과 추상화 비용이 지나치게 커진다. 따라서 **업무 단위 계약을 필요한 곳에만 추가하는 점진적 구조**를 선택한다.

```text
API / CLI 구성
    → 분석 서비스: 작업 흐름과 업무 경계
        → 그래프: 단계와 분기 / 모델·API 어댑터
        → 저장소 계약 → SQLite 구현
공통 실행 규칙·내부 타입 ← 서비스 / 그래프 / 저장소
순수 계산·근거 색인 ← 원자료 (네트워크·DB를 모름)
```

- 그래프의 함수 주입, LangGraph, RunHooks, SourceIndex는 유지한다.
- composition root는 API·CLI 시작 지점이다. 설정에서 구현을 선택하는 작업은 여기에 연결된 생성기 구성 함수가 담당한다.
- 저장소는 서비스/API를 import하지 않는다. 공통 정책도 sqlite3·FastAPI를 import하지 않는다.
- 현재 저장소가 제공하는 `complete_request`, `claim_question_resume`, `claim_decision_retry` 같은 업무 단위 트랜잭션은 유지한다.
- 범용 BaseService, BaseRepository, 모든 도구의 클래스화, 전역 Singleton은 도입하지 않는다.

## 4. 저장소 계약과 트랜잭션

### 4.1 계약의 크기

`app/storage/contracts.py`에 동기 `AnalysisRepositoryProtocol(typing.Protocol)`을 두고, `app/db/analysis_repository.py`의 `SqliteAnalysisRepository`가 기존 저장 함수에 위임한다. 동기 계약을 선택하는 이유는 기존 SQLite 실행을 서비스의 `asyncio.to_thread()`로 격리하고 취소 시 `_settle()` 동작을 보존하기 위해서다.

계약은 서비스가 사용하는 업무 동작만 포함한다. 전체 기존 함수를 미리 추상화하지 않는다. 첫 도입은 조회·완료·재개 claim이다.

- `get_detail(request_id: str) -> StoredAnalysisDetail | None`
- `complete(result: DecisionResult, *, attempt: int, source_attempts: dict[str, int]) -> None`
- `claim_answers(submission: AnswerSubmission) -> bool`
- `load_resume(request_id: str) -> ResumeBundle`
- `claim_retry(request_id: str, failed_at: str) -> ResumeBundle`

기존 claim 인자 조합을 어댑터가 전달하며 기존 함수의 사전 검사·문구·잠금을 보존한다. 저장 이벤트·예산 갱신까지 이관하는 후속 단계에서 실제 호출에 필요한 메서드만 추가한다. 단일 모델을 CRUD 인터페이스로 억지 변환하지 않는다.

### 4.2 타입과 반환 경계

`app/storage/models.py`에 업무 조회 타입을 정의한다. `StoredAnalysisDetail`은 요청 상태·역사적 JSON 객체·분석 이력·질문·지도·평가·브리핑을 명시적 필드로 제공한다. SQL 열 이름과 `_json` 문자열은 SQLite 어댑터 안에서 끝난다.

과거 최종 결과는 저장 당시 JSON 객체로 반환한다. 새로운 DecisionResult로 재검증해 옛 결과를 바꾸지 않는다. 그래프 실행에 다시 쓰는 재개 자료는 별도의 엄격한 복원 검증을 적용한다.

### 4.3 원자성

claim, 완료 이력과 최신 상태 갱신, 보완 이력과 분석 차수 저장은 각각 같은 트랜잭션에서 성공하거나 롤백되어야 한다. 현재 이미 그렇게 구현된 동작은 유지한다. 서비스에서 BEGIN/COMMIT하거나 외부 API를 호출한 채 DB 트랜잭션을 열어 두지 않는다.

범용 UnitOfWork는 도입하지 않는다. 업무 동작 하나의 트랜잭션으로 표현되지 않는 실제 요구가 생길 때 별도 결정한다.

## 5. 내부 상태와 복원

- LangGraph에는 TypedDict를 유지한다. 자유 형식 `AgentAnalysis.data`까지 한꺼번에 모델로 바꾸지 않는다.
- `GraphState`는 실행 상태, `GraphUpdate`는 노드가 반환하는 부분 변경분으로 구분한다. task/analyses는 주소·분석 노드 이전에는 존재하지 않으므로 전체 그래프에서 Required로 강제하지 않는다.
- `validate_resume_state(state, *, mode, retry_only)`에서 task·analyses의 계약과 ID, 지도 타입, 라운드 범위, 평가 조합을 검사한다. 판단 가능한 상태 조합은 기존 실행 테스트에서 추출한다.
- 옛 context를 옮기는 `normalize_resume_state`는 순수 호환 변환이다. 변환 후 검증하고 실행한다. cast로 검증을 대신하지 않는다.
- 빈 목록, 자료 없음(None), 아직 실행하지 않음, 조회 실패를 구분한다. `.get()`은 정말 선택적인 필드에만 사용한다.
- 실행 JSON의 예산·시간·capabilities는 복원 입구에서 검증한다. 값 보정으로 손상을 숨기지 않는다.
- 병렬 노드는 자기 자료 변경분을 반환하고 한곳에서 합친다. 서로의 자료를 덮어쓰지 않는 현재 규칙을 보존한다.

## 6. 실행·오류·취소 책임

- 서비스는 요청 실행·재개·실패 저장의 책임을 가진다. 생성기 구성과 DB 콜백 조립은 별도 모듈로 옮긴다.
- 전문가 반복 실행은 유지하되 도구 응답 해석과 finish 내용 검증을 순수 함수로 분리한다.
- `DecisionExecutionError`는 원래 실패와 정제된 진단 목록을 명시적으로 보관한다. CancelledError는 일반 실패 타입으로 바꾸지 않고 전파하며 서비스의 finally 경로에서 진단을 보존한다.
- 일반 외부 실패, 계약 손상, 저장 실패, 취소를 분리한다. 공개 오류 변환의 코드·문구는 유지한다.
- 모델 원문, 사용자 원문, 키, API URL의 키 부분은 로그·메트릭에 넣지 않는다.
- fallback으로 전환해도 코드가 생성한 제외 경고와 호출 기록을 보존한다.
- 저장 정책의 기존 sqlite3 오류를 공통 정책 밖의 SQLite 어댑터에서 변환해 외부 동작을 유지한다.

## 7. 작업 관리와 제한

### 7.1 A부: 단일 프로세스

`app/services/jobs.py`의 `AnalysisJobRegistry`가 작업 등록·제거·제한·종료를 소유한다. 동일 요청 ID로 살아 있는 작업을 덮어쓰지 않고, 콜백은 자신이 등록한 작업일 때만 제거한다. 기존 충돌 응답을 재사용하고 새 응답 형태를 만들지 않는다.

새 분석·답변 재개·판정 재시도 및 wait=true/false가 모두 같은 실행 슬롯을 사용한다. 제한은 접수 전에 적용한다. wait=false의 기존 429와 요청 ID 헤더를 유지한다. wait=true에도 같은 제한을 적용하는 것은 과부하 버그 수정으로 별도 테스트한다.

서버 종료는 접수를 막고, 작업을 취소한 뒤 정리 종료를 기다린다. 종료 대기 상한은 내부 기본값 10초로 두고, 저장 스레드를 강제로 중단할 수 있다는 가정을 하지 않는다. `_settle`의 일관성 보장은 유지한다.

다중 워커·다중 서버 지원은 A부 완료로 주장하지 않는다. A부 동안 `fail_interrupted`와 메모리 작업표의 단일 프로세스 제약을 문서화한다.

### 7.2 B부: 여러 프로세스

API는 영속 접수 후 202를 반환하고 제한된 워커가 작업을 처리한다. 큐는 중복 배달될 수 있다고 가정한다. 요청 ID·실행 차수 기반 원자적 claim, 소유자·lease·heartbeat, 재시도 단계 보존이 필요하다.

시작 시 모든 running 요청을 실패 처리하는 로직은 lease가 만료된 작업만 복구하는 방식으로 교체한다. 시간·예산은 워커 교체 후에도 이어 쓰며 이미 완료한 평가·원자료를 불필요하게 다시 호출하지 않는다. 중단 시 외부 LLM 호출이 이미 과금되었을 가능성을 고려한다.

작업 중복 방지 키와 HTTP request_id는 분리한다. 사용자·정규화 좌표·반경·기간·기능 설정·자료 버전·모델/프롬프트 버전이 결과 재사용 범위를 결정한다. 개인정보와 임대인 답변은 사용자 간 공유 캐시에 넣지 않는다.

## 8. 근거와 수치

A부에서는 경로 검증·숫자 검증·경고 생성을 분리하고 명백한 정규식 오인만 수정한다. 지표 간 숫자 뒤바뀜을 현재 방식으로 완전히 검증할 수 있다고 주장하지 않는다. 기존 정규식에 계속 예외를 붙이지 않는다.

B1은 report-plan의 Figure와 통합한다. 서버가 근거 ID·경로·소유 업종·값·단위·자료 버전을 갖는 내부 EvidenceFact를 만든다. 모델은 허용된 근거를 선택하고 서버가 값을 채운다. 근거 ID는 해당 입력 스냅샷 안에서만 유효하다.

비율·거리·표본 수·문맥 반경도 명시적 종류로 구분한다. 집계와 환산이 필요하면 코드가 허용한 연산·입력·분모만 사용한다. arbitrary 계산식을 받지 않는다. 구조화 필드와 자유 문장 숫자를 따로 반환해 검증을 우회하지 않도록 숫자는 검증된 템플릿/표현에서 렌더링한다.

Structured Outputs는 구조 보장이지 진실성 보장이 아니다. 서버·모델별 지원을 오프라인 대역으로 확인하고, 실제 서버 지원은 별도 승인된 최소 실측으로 검증한다. 기존 스키마와 저장 이력의 호환·버전 정책을 결정하기 전에는 공통 계약을 바꾸지 않는다.

## 9. 효율과 자원 수명

- 평가자 공통 입력과 색인은 한 평가 라운드에서 한 번 생성한다. 개별 평가자의 식별자만 추가한다.
- 보완·지도 채택으로 원자료가 바뀌면 색인과 입력을 갱신한다. 객체 주소만으로 장기 캐시하지 않는다.
- LLM/HTTP 클라이언트는 설정과 이벤트 루프 수명 안에서 재사용하고 종료 시 닫는다. 다른 키·base URL의 클라이언트를 섞지 않는다. 전역 무제한 풀은 금지한다.
- API별 제한과 총 LLM 토큰/요청률 제한은 B2에서 공유한다. 요청별 예산과 서비스 전체 제한은 별개다.
- 재시도는 일시 실패에만 상한·지연·무작위 분산을 둔다. 기존 SDK 재시도와 앱 재시도가 겹쳐 비용이 늘지 않게 한다.
- CSV/SHP·catalog는 현재 생성/로딩 방식을 유지한다. 로딩 횟수·메모리를 측정하기 전 지리 라이브러리를 새로 넣지 않는다.

## 10. 규모·진행 조회·관측

동시 접속자, 폴링 사용자, 초당 신규 분석, 실행 중 분석을 구분한다. 1만/10만 명을 처리한다고 주장하려면 사용자 구성·외부 API 한도·토큰 예산·하드웨어·SLO를 먼저 정해야 한다.

3초 폴링 시 1만 명은 약 3,333 RPS, 10만 명은 약 33,333 RPS이다. 평균 80초와 19 LLM 호출을 가정한 동시 분석 1만 건은 약 125 완료/초·2,375 LLM 호출/초를 요구한다. 이 값은 산술 예시이고 수용량 측정이 아니다.

- A12: 네트워크·유료 모델 없이 대역 부하 측정. 실행/조회 각각 10·50·100 동시 요청을 측정한다. 외부 장애·느린 DB·취소를 포함한다.
- 기록: 접수 성공·제한·오류, 큐/실행 시간 p50/p95/p99, event-loop 지연, CPU/RSS, DB 잠금/조회 시간, 호출·토큰 수.
- 사용자 ID나 요청 ID를 메트릭 라벨로 쓰지 않는다. 상관관계는 정제된 로그·trace로 남긴다.
- SQLite WAL은 다중 작성자를 동시에 처리하지 않는다. B2에서는 PostgreSQL 등 서버형 DB와 큐를 비교한다. 제품 선택은 부하 결과·운영 비용 후 결정한다.
- B3: 가벼운 폴링부터 간격 증가·분산·종료·숨김 탭 정책을 계약으로 정한다. 프론트 구현은 별도 작업이다.
- SSE는 새 이벤트 푸시·재접속 커서·keepalive·취소·프록시 설정을 함께 설계한다. 모든 SSE 연결이 매초 DB를 조회하는 구현은 해결책이 아니다. 다중 워커에서는 공유 이벤트 전달이 필요하다.
- `after`의 순번과 완료 이벤트 보존, 이벤트 보관 기간, 최대 페이지 크기를 결정한다. 기존 응답 변경은 B3 합의 대상이다.

공개 운영에는 사용자/조직별 조회 소유권과 호출 할당량이 필요하다. UUID의 추측 어려움은 권한 검사가 아니다. 인증 제공자·원자료 이용 조건·과금 정책은 배포 대상이 정해진 뒤 결정한다.
