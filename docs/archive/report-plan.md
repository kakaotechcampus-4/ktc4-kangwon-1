작성: 2026-10-02 · 상태: **구상(사용자 검토 전)** · 범위: 최종 리포트의 내용·형식
관련: `backend/app/schemas.py`(DecisionResult), `docs/evaluation-plan.md`(평가자), `docs/map-search-plan.md`(지도)

## 0. 왜 다시 구상하나

지금 리포트는 업종마다 **점수 · 이유 문장 · 근거 경로 · 위험 문장**뿐입니다.
실측(오금로 404, `19d96772`)에서 평가자 4명이 공통으로 짚은 것은 "틀렸다"가 아니라 **"빠졌다"**였습니다.

| 평가자 | 실제 지적 | 리포트에 빠진 것 |
| --- | --- | --- |
| 동네 손님 | 세탁업 근거가 상주인구·안정성에 치우침. 실제 이용 고객(가구·직장인)의 이용 시간대와 맞는지 확인 안 됨 | **주 고객층과 이 동네의 일치도, 시간대** |
| 동네 손님 | 음료점은 10대 통행을 근거로 들었지만 오후·저녁 통행은 서울 평균보다 낮고 유동도 감소 | **추세, 시간대 적합성** |
| 예비 창업자 | 음료점 순증 3개소는 개업 10·폐업 8의 결과. 500m 안 34개소 | **교체율, 경쟁 강도** |
| 심사자 | 세탁업 폐업률 0%는 점포 6개 기준이라 표본이 작음 | **근거 신뢰도** |
| 임대인 대변인 | 세탁·음료·교육·미용 모두 급배수·전기·환기·층수·면적 확인 필요 | **공간·설비 조건, 임대인 확인 목록** |

즉 판정관이 판단은 했지만, **임대인이 "그래서 이 업종을 받아도 되나"를 결정하는 데 필요한 항목**을 매번 같은 틀로 쓰지 않습니다.
이 문서는 그 틀을 정합니다.

## 1. 원칙

1. **추천 Top 5, 비추천 Top 5.** (지금 형식도 최대 5개지만 화면은 3개만 씀. 5개를 기본으로 채움)
2. **업종마다 같은 항목을 같은 순서로.** 임대인이 업종끼리 비교할 수 있어야 합니다.
3. **숫자는 코드가, 해석은 모델이.** 점포 수·비율·거리·고객 비중 같은 숫자 칸은 원자료 경로에서 코드가 채웁니다. 모델은 그 숫자를 풀어 쓴 문장과 판단만 씁니다. (브리핑의 "주장 + 근거 경로" 원칙을 리포트 칸까지 확장)
4. **자료가 없으면 "확인 필요"라고 쓰고 지어내지 않습니다.** 예: 매출·임대료(자료 없음), 점포 면적(임대인 질문).
5. **상권을 모르는 사람이 읽습니다.** 모든 숫자 옆에 뜻을 한 줄로. "LQ 1.41" 대신 "주변 2km 평균보다 1.4배 많이 모여 있음".
6. **점수는 성공 확률이 아닙니다.** (기존 원칙 유지)

## 2. 리포트 구성

```
A. 한 줄 결론
B. 이 동네는 어떤 곳인가 (동네 프로필)
C. 추천 업종 Top 5   ← 업종마다 C1~C8 같은 틀
D. 비추천 업종 Top 5 ← 업종마다 D1~D5
E. 임대인 확인 목록 (C·D의 공간 조건·질문을 모음)
F. 평가자 의견과 판정관 반영 (구현됨)
G. 자료 한계와 출처
```

### A. 한 줄 결론
- 예: "주거 중심 · 학생 통행이 많은 동네라 생활 서비스는 맞지만, 음식·음료는 이미 촘촘합니다. 1순위 세탁업(설비 확인 조건)."
- 출처: 판정관 문장. 숫자 없이 씁니다(숫자는 B·C에서).

### B. 이 동네는 어떤 곳인가

| 항목 | 말할 것 | 원자료 (현재 있음) |
| --- | --- | --- |
| 누가 사나 | 상주인구, 가구 수, 가구당 인원, 연령 비중 | 유동인구 `resident.count·households·persons_per_household·age_share` |
| 누가 일하나 | 직장인구, 연령 비중 | `worker.count·age_share` |
| 누가 지나가나 | 일평균 유동, 연령·성별 비중, 유형(학생형 등) | `population.daily_avg·age_share·female_ratio`, `type` |
| 언제 붐비나 | 가장 붐비는 시간대, 시간대별 비중, 주말/평일 | `population.peak_time_band·time_per_hour_share·weekend_to_weekday_ratio` |
| 늘고 있나 | 직전 분기 대비 추세 | `trend` |
| 서울과 비교 | 서울 평균 대비 높은/낮은 지표 | `benchmark` |
| 상권 성격 | 가장 가까운 상권 이름·종류(발달상권 등), 반경 500m 점포 수, 많은 업종·특화 업종 | 상권 `trade_areas`, `store_total`, `by_radius.top_by_count·top_by_specialization` |

화면: 카드 4~5개(사는 사람 / 일하는 사람 / 지나가는 사람 / 시간대 / 상권). 각 카드에 숫자 1~2개 + 풀어 쓴 문장 1개.

### C. 추천 업종 Top 5 — 업종마다

| # | 항목 | 말할 것 | 숫자 출처 (코드) | 문장 (모델) |
| --- | --- | --- | --- | --- |
| C1 | 한 줄 이유 | 왜 이 자리에 맞나 | — | 판정관 |
| C2 | **주 고객층과 일치도** | 이 업종의 주 고객(예: 1~2인 가구·맞벌이) → 이 동네에 얼마나 있나 → **맞음 / 일부 / 안 맞음** | 고객층에 해당하는 B의 지표(가구당 인원, 연령 비중, 직장인 수) | 일치 판단과 이유 |
| C3 | **이용 시간대 적합성** | 이 업종 손님이 오는 시간대(예: 세탁 = 출근 전·퇴근 후·주말) vs 이 동네가 붐비는 시간대 | `time_per_hour_share`, `peak_time_band`, `weekend_to_weekday_ratio` | 맞는지 판단 |
| C4 | **경쟁** | 반경 50·200·500m 동종 점포 수, 주변 2km 대비 밀집(배), **가장 가까운 동종 점포 이름·거리 3곳** | 상권 `by_middle.count·lq`, `by_radius`, 지도 `industries.{코드}`·`places` | 경쟁이 센지·빈자리가 있는지 |
| C5 | **버티는가** | 최근 1년 개업·폐업 수, 순증감, 12분기 추세, 교체율 | 개폐업 `metrics.*` | "늘고 있음/교체가 잦음" 해석 |
| C6 | **공간·설비 조건** | 이 업종에 필요한 설비(급배수·전기 용량·환기·층·면적·소음) 중 **확인이 필요한 것** | 업종 설명표(4장) | 임대인에게 왜 확인해야 하는지 |
| C7 | 위험과 조건 | 이 업종이 실패하는 전형적 이유와 "이 조건이면 해볼 만함" | — | 판정관 (평가자 지적 반영) |
| C8 | **근거 신뢰도** | 높음 / 보통 / 낮음 + 이유(점포 수가 적음, 지도 표본, 자료 기간 등) | 코드 규칙(5장) | — |

### D. 비추천 업종 Top 5 — 업종마다

| # | 항목 | 말할 것 |
| --- | --- | --- |
| D1 | 한 줄 이유 | 왜 이 자리에 안 맞나 |
| D2 | 걸리는 지점 | 과밀(C4) / 폐업 증가(C5) / 고객층 불일치(C2) / 공간 불가(C6) 중 무엇인지 **유형으로** 표시 |
| D3 | 숫자 근거 | 걸리는 지점의 숫자 (C와 같은 출처) |
| D4 | 다시 볼 조건 | "1층·급배수가 있으면 다시 검토" 같은 조건 (없으면 비움) |
| D5 | 근거 신뢰도 | C8과 같은 규칙 |

### E. 임대인 확인 목록
- C6·D4와 판정관 질문을 **질문 하나당 한 줄**로 합칩니다. 어느 업종 때문에 필요한지 꼬리표를 붙입니다.
- 예: "급배수 설비가 있나요? (세탁업 · 미용업 · 음료점)" / "전용면적은 몇 m²인가요? (교육 · 미용)"
- 이미 임대인이 답한 질문은 답과 함께 "확인됨"으로 표시합니다.

### F. 평가자 의견과 판정관 반영
- 구현됨(`docs/evaluation-plan.md`). 의견 전부 + 지적마다 반영 / 일부 반영 / 반영 안 함.
- 추가: 각 지적이 C1~C8 중 **어느 칸에 반영됐는지** 표시(4장 형식에 `applied_to` 추가 검토).

### G. 자료 한계와 출처
- 출처·기간: 생활인구(분기), 상가정보(기준일), 개폐업(12분기), 지도(조회 시각, 첫 페이지 표본).
- **자료가 없는 것을 명시:** 매출, 임대료, 권리금, 점포 면적·층(질문으로만), 규제·인허가(다른 팀원 기능 연결 예정).

## 3. 형식 변경안 (`schemas.py`, PR 합의 필요)

추가 방식으로 바꿔 옛 저장 결과도 그대로 읽히게 합니다. `schema_version`은 `"1.1"`을 새로 허용합니다.

```python
class Figure(Schema):          # 코드가 채우는 숫자 칸 하나
    label: Text                # "반경 500m 동종 점포"
    value: float | int | Text
    unit: Text | None          # "개", "%", "m", "배"
    evidence: Evidence         # 원자료 경로(코드가 값과 함께 검증)
    plain: Text | None         # 풀어 쓴 한 줄(코드 템플릿 또는 모델)

class CustomerFit(Schema):     # C2·C3
    segments: list[Text]       # "1~2인 가구", "맞벌이 직장인"
    match: Literal["high", "partial", "low", "unknown"]
    time_fit: Literal["high", "partial", "low", "unknown"]
    figures: list[Figure]
    explanation: Text

class Competition(Schema):     # C4
    figures: list[Figure]      # 50·200·500m 수, 밀집 배수
    nearest: list[Figure]      # 지도 장소 이름·거리(최대 3)
    explanation: Text

class Stability(Schema):       # C5
    figures: list[Figure]
    explanation: Text

class SpaceNeed(Schema):       # C6
    item: Literal["water", "power", "ventilation", "floor", "area", "noise", "other"]
    question: Text             # 임대인에게 물을 문장
    why: Text

class Confidence(Schema):      # C8
    level: Literal["high", "medium", "low"]
    reasons: list[Text]

class IndustryAssessment(Schema):   # 기존 필드 유지 + 선택 필드 추가
    category, score, reasons, evidence, risks          # 그대로
    customer_fit: CustomerFit | None = None
    competition: Competition | None = None
    stability: Stability | None = None
    space_needs: list[SpaceNeed] = []
    conditions: list[Text] = []                        # C7 "이 조건이면 해볼 만함" / D4
    blockers: list[Literal["saturated", "declining", "customer_mismatch", "space"]] = []  # D2
    confidence: Confidence | None = None

class NeighborhoodProfile(Schema):  # B
    cards: list[{title, figures: list[Figure], explanation}]

class DecisionContent(Schema):
    ...기존...
    headline: Text | None = None                       # A
    neighborhood: NeighborhoodProfile | None = None    # B
    landlord_checklist: list[{question, for_codes: list[IndustryCode], answered: Text | None}] = []  # E
```

**채우는 방법 (핵심 결정)**
- `Figure`는 **모델이 경로만 고르고 값은 코드가 채웁니다.** 모델이 숫자를 직접 쓰지 않으므로 "숫자·단위 불일치"로 버려지는 일이 구조적으로 사라집니다.
- `match`·`time_fit`·`level`·`explanation`은 모델이 씁니다. 평가자가 이 칸들을 지적합니다.
- `Confidence.level`은 코드 규칙(5장)으로 상한을 정하고, 모델은 그보다 낮게만 바꿀 수 있습니다.

## 4. 업종 설명표 확장 (`INDUSTRY_PROFILE`, 75개)

C2·C3·C6은 "이 업종의 손님은 누구이고, 언제 오고, 무엇이 필요한가"라는 **업종 지식**이 필요합니다.
모델이 매번 알아서 판단하게 두면 같은 업종인데 실행마다 말이 달라집니다. 지도 때 만든 `INDUSTRY_TERMS`처럼 표로 둡니다.

| 칸 | 예 (S209 세탁업) |
| --- | --- |
| 주 고객층 | 1~2인 가구, 맞벌이 직장인, 주거 밀집 |
| 관련 동네 지표 | `persons_per_household`(낮을수록 유리), `resident.households`, `worker.count` |
| 주 이용 시간대 | 07~09시, 18~21시, 주말 |
| 필요 설비 | 급배수·배수구, 전기 용량, 환기 |
| 층 선호 | 1층 (수거·배달형은 무관) |

- 만드는 법(제안): 모델로 75개 초안 생성 → **사람이 검수** → `industries/data/industry_profile.csv` → 생성 스크립트가 `catalog.py`에 넣음(`INDUSTRY_TERMS`와 같은 경로, `--check` 검사).
- 임대인 대변인 평가자와 판정관이 같은 표를 보므로 공간 조건 지적이 일관됩니다.

## 5. 근거 신뢰도 규칙 (코드)

| 조건 | 상한 |
| --- | --- |
| 개폐업 최신 점포 수 < 10 | 보통 |
| 개폐업 `confidence == "low"` 또는 점수 없음 | 낮음 |
| 경쟁 근거가 지도 표본뿐 | 보통 |
| 유동인구 `reliability`가 낮음 | 보통 |
| 핵심 칸(C2·C4·C5) 중 2개 이상 `unknown` | 낮음 |

이유 문장도 코드가 붙입니다(예: "이 업종 점포가 6개뿐이라 폐업률을 일반화하기 어렵습니다").

## 6. Top 5로 늘릴 때 영향

| 대상 | 영향 | 대응 |
| --- | --- | --- |
| 판정관 | 10개 업종 × 칸 8개 → 출력이 길어짐 | 스트리밍 사용 중이라 토큰 제한 문제 없음. 출력 토큰 상한 확인 |
| 평가자 | 입력 커짐, 지적이 많아짐 | 평가자당 지적 상한(현재 4) 유지 또는 6으로 |
| 업종이 5개가 안 될 때 | 근거 있는 업종이 적은 동네 | 최소 개수 강제하지 않고 "근거 있는 업종이 N개뿐"을 G에 명시 |
| 프론트 | Top 3 → Top 5, 칸별 카드 | 리포트 화면 재설계 필요 |
| 근거 검증 | `Figure` 경로 검증 | 기존 `index_paths`·`valid_map_path` 재사용, 값은 코드가 채우므로 숫자 검사 불필요 |

## 7. 정해야 할 것 (사용자)

1. **B~G 구성과 C1~C8·D1~D5 항목**이 맞는지, 빼거나 더할 항목.
2. **숫자는 코드가 채우는 방식(3장 `Figure`)**으로 갈지. (추천: 예)
3. **업종 설명표(4장)**를 만들지, 누가 검수할지.
4. 매출·임대료처럼 **자료가 없는 항목**을 리포트에 "확인 필요"로라도 노출할지.
5. 평가자 지적의 `applied_to`(어느 칸에 반영됐는지) 표시 여부.
6. 화면: 업종 카드를 펼치는 방식 / 업종 비교 표 방식.
