# 같은 주소 반복 분석 실측 (11/07 구조 변경 뒤)

검증일: 2026-11-11

## 결론

서울 세 곳을 같은 입력으로 세 번씩, 모두 아홉 번 실제 모델로 분석했다.

| 확인한 것 | 결과 |
| --- | --- |
| 추천 5개(Top5) | 세 곳 모두 세 번의 순서·배지가 같았다. 같은 날 뒤의 재측정 여섯 번 중 한 번은 2·3위가 바뀌었다 |
| L 등급(판단 10점) | 51업종 × 9번 모두 같은 주소 안에서 같았다(최대 차 0). 같은 날 뒤의 재측정 여섯 번 중 두 번은 달랐다(최대 차 1) |
| 평가자 4명 완료 | 36자리 중 35자리 완료. 1자리는 역할 예산 초과로 실패 |
| 평가자 판단 | 같은 주소 안에서 세 번 같았다(실패한 1자리 제외) |
| 평가 의견 최종 반영 | 9번 중 6번 완료, 3번은 반영하지 못하고 직전 초안으로 마무리 |

처음 아홉 번에서는 Top5와 L이 흔들리지 않았다. 다만 L의 일치는 AI 판단이 안정적이라는 증거로는 약하다. 이번 입력에서 AI가 L 근거로 쓸 수 있는 자료가 사실상 하나였기 때문이다. 실제로 뒤의 재측정에서는 같은 근거를 유리로 볼지 중립으로 볼지가 달라진 실행이 나왔다([아래 2번](#2-l-일치는-입력이-좁아서-생긴-결과에-가깝다)).

새로 드러난 문제는 마지막 반영 단계의 예산이다. 첫 제출이 형식 오류로 거절되면 다시 제출할 여유가 없어, 평가자 지적 처리 기록이 빈 채로 끝난다([아래 1번](#1-마지막-반영-단계는-사실상-한-번만-시도할-수-있다)). 같은 날 예산을 고치고 다시 쟀다([고친 것과 재측정](#고친-것과-재측정-같은-날)).

## 발견한 문제

### 1. 마지막 반영 단계는 사실상 한 번만 시도할 수 있다

평가자 의견을 받아 최종 보고서를 다시 내는 단계는 별도 예산이 있다. 호출 2번, 입력 5만 토큰이다([backend/app/ai/budget.py](../backend/app/ai/budget.py)의 `DECISION_PHASE_LIMITS`). 예산은 호출 전에 입력 글자 수로 토큰을 미리 어림하고, 끝난 호출은 실제 토큰으로 센다.

- 이 단계의 첫 호출은 실제 입력 2.3만~2.9만 토큰을 썼다. 5만에서 빼면 두 번째 호출에 남는 자리는 2.1만~2.7만이다.
- 첫 호출의 사전 어림값은 3.0만~4.0만이었다. 아홉 번 모두 이것만으로 남은 자리를 넘었다.
- 두 번째 호출은 첫 호출의 대화와 거절 사유가 더해져 더 길다. 그래서 어느 실행에서도 두 번째 호출을 시작할 수 없다.

호출 2번을 허용한 설정과 달리, 실제로는 한 번만 시도할 수 있다. 첫 시도가 실패한 세 번은 다음과 같다.

| 실행 | 첫 시도에서 일어난 일 | 결과 |
| --- | --- | --- |
| 오금로 1번째 | 근거 문장 칸에 표시 형식(`format`)이 빠져 제출 거절 | 재시도가 예산에 막혀 직전 초안으로 마무리 |
| 오금로 2번째 | 제출하지 않고 자료 조회 도구를 부름 | 같음 |
| 테헤란로 3번째 | 오금로 1번째와 같은 형식 오류 | 같음 |

세 번 모두 Top5와 L은 바뀌지 않았다. 바뀐 것은 다음 두 가지다.
- 평가자 지적의 처리 기록(받아들임·일부 받아들임)이 비었다.
- 보고서 한계 칸에 "피드백 최종 반영을 완료하지 못했습니다"가 붙었다.

사용자에게 숨겨지지는 않지만, 아홉 번 중 세 번은 네 평가자의 검토가 최종 보고서 문장에 들어가지 않았다.

### 2. L 일치는 입력이 좁아서 생긴 결과에 가깝다

아홉 번 모두 51업종의 L 근거가 정확히 하나였다. 43업종은 "면적 조건 일치"(3등급), 8업종(G211·I101·I102·I207·M111·Q102·R103·S203)은 "면적 조건 불일치"(1등급)였다. 세 주소가 같은 8업종을 1등급으로 받았다. 주소와 상관없이 50㎡라는 같은 입력에서 나온 판단이기 때문이다.

이렇게 된 이유는 설계에 있다.
- AI는 업종마다 어떤 근거를 어느 방향으로 쓸지만 고른다. 등급 숫자와 근거 문장은 코드가 만든다([backend/app/domain/l_record.py](../backend/app/domain/l_record.py)).
- 층과 코드가 이미 채점한 설비는 L 근거로 쓸 수 없다. 같은 사실을 두 번 세지 않기 위해서다([backend/app/domain/report.py](../backend/app/domain/report.py)의 `rule_scored_space`).
- 1층·50㎡·설비 미입력이면 남는 근거가 면적 하나뿐이다.

따라서 "L 등급 차이 0"은 이 입력 조건에서 AI가 고를 것이 적었다는 뜻에 가깝다. 고를 것이 전혀 없지는 않다. 같은 면적 근거를 유리로 낼지 중립으로 낼지는 모델이 정하며, 같은 날 뒤의 재측정에서 실제로 달라졌다([아래](#거절-안내와-지시문-수정-뒤-재측정-같은-날)). 근거가 여러 개인 조건에서 L이 얼마나 흔들리는지는 이번에 재지 못했다.

### 3. 평가자 역할 예산 초과 1건

테헤란로 2번째에서 심사관 평가자는 자료를 크게 한 번 읽은 뒤(입력 약 2.1만 토큰), 다음 호출이 심사관 몫의 입력 한도 4만 토큰을 넘어 실패했다(`BUDGET_EXCEEDED`). 나머지 세 평가자는 끝났고, 보고서의 평가 완료율은 0.75로 표시됐다.

## 고친 것과 재측정 (같은 날)

1번 문제를 고쳤다([backend/app/ai/budget.py](../backend/app/ai/budget.py)).

| 항목 | 전 | 후 |
| --- | --- | --- |
| 마지막 반영 단계 몫 | 입력 5만·출력 6천·2호출 | 입력 9만·출력 1만·2호출 |
| 분석 1회 전체 상한 | 입력 40만·출력 6만 | 입력 44만·출력 6.4만 |

다른 역할의 몫은 그대로다. 역할 몫의 합이 전체 상한과 같도록 나눈 기존 구조를 지키려고 전체 상한도 함께 올렸다. 평소 비용은 같고, 첫 시도가 실패해 두 번째 시도를 할 때만 입력 약 2.6만~2.8만 토큰이 더 든다.

추가한 시험:
- 예산 시험: 첫 시도가 입력 2.9만·출력 3,600(오늘 실측 최대 수준)을 써도 두 번째 시도 자리가 남는지 본다.
- 흐름 시험: 마지막 단계 대화가 약 5만 자일 때 첫 시도는 자료 조회, 두 번째 시도는 제출이다. 고치기 전 예산에서는 1번에서 멈춰 실패했고, 고친 뒤에는 반영까지 끝나 통과했다.

재측정은 오금로 404를 같은 조건으로 세 번 돌렸다.

| 실행 | 마지막 단계 | 결과 |
| --- | --- | --- |
| 1번째 | 1차·2차 모두 거절(일부 반영 칸 형식, 너무 짧은 문장 조각) | 반영하지 못함(호출 2번을 다 씀) |
| 2번째 | 1차 거절(일부 반영 칸 형식) → 2차 통과 | 지적 15건 처리 기록 |
| 3번째 | 1차 통과 | 지적 10건 처리 기록 |

- Top5·배지·L은 고치기 전과 같았다(세 번 모두 G215·I210·L102·G202·G204).
- 호출 16~19회, 84.2~136.2초가 걸렸다.

오금로의 반영 완료는 고치기 전 3번 중 1번, 고친 뒤 3번 중 2번이었다. 표본이 작아 비율이 나아졌다고 주장하지 않는다. 확인한 것은 두 번째 시도가 실제로 일어나고 성공할 수 있다는 점이다.

1번째처럼 모델이 거절 사유를 고치지 못하면 두 번째 시도도 실패한다. 이는 예산이 아니라 거절 안내와 제출 형식의 문제로 남긴다.

## 거절 안내와 지시문 수정 뒤 재측정 (같은 날)

마지막 단계에 두 번째 시도가 생긴 뒤에도 모델이 제출 양식을 두 번 다 틀리면 반영이 빠졌다. 12번의 실행에서 보고서 제출 30번 중 11번이 거절됐고, 원인을 보니 안내가 부족했다.

| 원인 | 고친 것 |
| --- | --- |
| 마지막 단계 지시문에 양식 규칙이 없었다 | 일부 반영이면 `applied`·`not_applied`를 모두 채우기, 기각이면 근거 `fact_ids`, 빈 text 금지, fact 조각의 `format`을 지시문에 적었다 |
| 거절 안내가 틀린 곳을 앞의 3개까지만 보여 줬다(마지막 단계 거절 5번 중 4번이 3개로 꽉 참) | 8개까지 보여 주고 같은 종류는 한 줄로 묶었다 |
| 거절 문장이 무엇을 고칠지 말하지 않았다 | 빈 문자열·빠진 칸·`format` 허용 값·일부 반영 규칙에 고치는 법을 붙였다 |
| 숫자 거절(초안 단계, 6번으로 가장 잦음)이 어느 문장인지 알려 주지 않았다 | 숫자가 든 text의 위치를 알려 준다. 문장 자체는 되돌려 보내지 않는다 |

- 오류 안내 상한은 300자에서 600자로 올렸다. 안내를 만드는 함수는 400자까지 만들 수 있었는데 응답 계약은 300자여서 어긋나 있었고, 둘을 600자로 맞췄다.
- 에이전트 구조와 예산은 바꾸지 않았다.

- 세 번 모두 평가 의견이 반영됐고, 마지막 단계 제출이 양식 때문에 거절된 적은 없었다.
- 호출 19~23회, 111.4~139.7초가 걸렸다.
- 표본이 세 번이라 거절이 줄었다고 단정하지 않는다. 고치기 전에는 같은 주소 여섯 번 중 세 번이 반영됐다.

이 재측정에서 두 가지가 더 드러났다.

**L 판단이 달라진 실행이 나왔다.** 2번째 실행에서 모델이 17개 업종의 "면적 조건 일치"를 유리가 아니라 중립으로 제출했다. 그 업종들의 L이 3등급에서 2등급으로 내려갔고, Top5의 2·3위(I210·L102)가 바뀌었다. 3번째 실행도 1개 업종이 중립이었다. L 제출은 이번에 고친 문장보다 앞 단계이고, 그때까지 모델이 받는 지시문과 도구 설명은 수정 전후가 같다(내용 비교로 확인). 오늘 15번 중 13번은 같았고 2번이 달랐으며, 등급 차는 최대 1이었다. 달라진 2번이 모두 마지막 세 번 안에서 나온 이유는 확인하지 못했다.

**자문역은 한도를 올린 뒤에도 한 번 실패했다.** 두 번 불려 한 번은 정상(849토큰), 한 번은 응답은 받았지만(918토큰, 길이 제한 아님) 답 검증에서 탈락해 자문 없음으로 처리됐다. 탈락 사유는 기록에 남지 않아 확인하지 못했다.

## 다른 단계의 같은 위험 점검

재시도할수록 대화가 길어지고 역할별 입력 몫이 있는 구조는 다른 단계에도 있다. 고치기 전 아홉 번의 기록으로 점검했다.

| 단계 | 입력 몫·설정 횟수 | 오늘 기록 | 판단 |
| --- | --- | --- | --- |
| 평가자 제출 재시도 | 각 4만·4번 | 제출이 거절되거나 읽기 3번을 채우면 몫 대신 전체 상한을 쓴다(`RuntimeBudget.submitting`). 임대인 평가자는 5.2만까지 써서 제출을 마쳤다 | 막히지 않음 |
| 평가자 읽기 단계 | 각 4만 | 심사관이 읽기 2번 뒤 세 번째 호출에서 1번 실패했다(3번 문제). 나머지 8번 중 4번도 읽기 도중 몫의 79~88%까지 찼다 | 막힘 있음. 심사관이 가장 위험. 같은 날 고침: 심사관 몫만 입력 4만→7만으로 늘리고 전체 상한을 44만→47만으로 올렸다. 실패한 경우는 약 5.6만, 큰 자료를 두 번 읽는 경우는 약 6.8만이 필요하다. 다른 평가자는 오늘 최대 2.9만~3.4만이라 그대로 뒀다 |
| 초안 단계 | 18만·20번 | 최대 9번·13.4만(74%). 많이 쓴 4번의 실행에서 오류·거절 뒤 재시도는 9회였고, 그중 6회가 보고서 제출 거절이었다. 보고서 제출 재시도는 한 번에 약 2만 토큰(1.9만~2.3만), 앞쪽 조회 재시도는 약 1.2만 토큰이 들었다 | 오늘은 막힌 적 없음. 호출 크기가 지금처럼 커진다고 어림하면, 가장 많이 쓴 실행은 10번째 호출까지 들어가고 11번째는 넘는다. 운영 화면은 추가 질문을 켜므로(이번 측정은 끔) 호출이 더 늘 수 있다 |
| 자문역 | 1만·2번 | 질문마다 따로 짧게 보내 쌓이지 않는다(한 번에 실제 2,398토큰, 몫의 약 24%) | 입력은 문제없음. 대신 두 번 모두 출력이 한도 1,000토큰에서 끝나 자문을 받지 못했다. 같은 질문·근거로 자문역만 다시 불러 확인했다: 한도 1,000은 길이 제한으로 중단(보이는 답 77자), 한도 4,000은 정상 완료·실제 1,808토큰. 같은 날 고침: 호출당 출력 1,000→3,000, 자문역 출력 몫 2천→6천, 전체 출력 상한 6.4만→6.8만. 고친 한도로 한 번 더 불렀을 때 2,045토큰·31.7초로 정상 완료했다. 대기 시간 상한 45초는 그대로라, 답이 2,900토큰 가까이 길어지면 시간 초과가 날 수 있다 |
| 전체 상한 | 47만·40번·600초 | 최대 22.3만·21번·140초 | 여유 있음 |
