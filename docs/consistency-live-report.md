# 같은 주소 반복 분석 실측 (11/07 구조 변경 뒤)

검증일: 2026-11-11

## 결론

서울 세 곳을 같은 입력으로 세 번씩, 모두 아홉 번 실제 모델로 분석했다.

| 확인한 것 | 결과 |
| --- | --- |
| 추천 5개(Top5) | 세 곳 모두 세 번의 순서·배지가 같았다 |
| L 등급(판단 10점) | 51업종 × 9번 모두 같은 주소 안에서 같았다(최대 차 0) |
| 평가자 4명 완료 | 36자리 중 35자리 완료. 1자리는 역할 예산 초과로 실패 |
| 평가자 판단 | 같은 주소 안에서 세 번 같았다(실패한 1자리 제외) |
| 평가 의견 최종 반영 | 9번 중 6번 완료, 3번은 반영하지 못하고 직전 초안으로 마무리 |

Top5와 L이 흔들리지 않은 것은 확인했다. 다만 L의 일치는 AI 판단이 안정적이라는 증거로는 약하다. 이번 입력에서 AI가 L 근거로 쓸 수 있는 자료가 사실상 하나였기 때문이다([아래 2번](#2-l-일치는-입력이-좁아서-생긴-결과에-가깝다)).

새로 드러난 문제는 마지막 반영 단계의 예산이다. 첫 제출이 형식 오류로 거절되면 다시 제출할 여유가 없어, 평가자 지적 처리 기록이 빈 채로 끝난다([아래 1번](#1-마지막-반영-단계는-사실상-한-번만-시도할-수-있다)).

- [decision 채점표](decision-prompt-rubric.md)는 "같은 주소 3회 L 등급 차이≤1, 평가자 타당 판정≥80%"를 L 배점 상향 검토 조건으로 적어 두었다. 지금까지 이 반복 측정을 한 적이 없다.
- 10/20 [임대인 입력 기록](landlord-context-live-report.md)은 주소마다 한 번씩만 돌렸다.
- 11/07에 `backend/app` 구조를 바꾼 뒤 실제 모델로 전체 분석을 다시 돌린 기록이 없었다.

## 발견한 문제

### 1. 마지막 반영 단계는 사실상 한 번만 시도할 수 있다

평가자 의견을 받아 최종 보고서를 다시 내는 단계는 별도 예산이 있다. 호출 2번, 입력 5만 토큰이다([backend/app/ai/budget.py](../backend/app/ai/budget.py)의 `DECISION_PHASE_LIMITS`). 예산은 호출 전에 입력 글자 수로 토큰을 미리 어림하고, 끝난 호출은 실제 토큰으로 센다.

- 이 단계의 첫 호출은 실제 입력 2.3만~2.9만 토큰을 썼다. 5만에서 빼면 두 번째 호출에 남는 자리는 2.1만~2.7만이다.
- 첫 호출의 사전 어림값은 3.0만~4.0만이었다. 아홉 번 모두 이것만으로 남은 자리를 넘었다.
- 두 번째 호출은 첫 호출의 대화와 거절 사유가 더해져 더 길다. 그래서 어느 실행에서도 두 번째 호출을 시작할 수 없다.

호출 2번을 허용한 설정과 달리, 실제로는 한 번만 시도할 수 있다. 첫 시도가 실패한 세 번은 다음과 같다.

| 실행 | 첫 시도에서 일어난 일 | 결과 |
| --- | --- | --- |
| 오금로 1번째 | 근거 문장 칸에 표시 형식(`format`)이 빠져 제출 거절 | 재시도가 예산에 막혀 직전 초안으로 마무리 |
| 오금로 2번째 | 제출하지 않고 자료 조회 도구를 부름 | 같음 |
| 테헤란로 3번째 | 오금로 1번째와 같은 형식 오류 | 같음 |

세 번 모두 Top5와 L은 바뀌지 않았다. 바뀐 것은 다음 두 가지다.
- 평가자 지적의 처리 기록(받아들임·일부 받아들임)이 비었다.
- 보고서 한계 칸에 "피드백 최종 반영을 완료하지 못했습니다"가 붙었다.

사용자에게 숨겨지지는 않지만, 아홉 번 중 세 번은 네 평가자의 검토가 최종 보고서 문장에 들어가지 않았다.

### 2. L 일치는 입력이 좁아서 생긴 결과에 가깝다

아홉 번 모두 51업종의 L 근거가 정확히 하나였다. 43업종은 "면적 조건 일치"(3등급), 8업종(G211·I101·I102·I207·M111·Q102·R103·S203)은 "면적 조건 불일치"(1등급)였다. 세 주소가 같은 8업종을 1등급으로 받았다. 주소와 상관없이 50㎡라는 같은 입력에서 나온 판단이기 때문이다.

이렇게 된 이유는 설계에 있다.
- AI는 업종마다 어떤 근거를 어느 방향으로 쓸지만 고른다. 등급 숫자와 근거 문장은 코드가 만든다([backend/app/domain/l_record.py](../backend/app/domain/l_record.py)).
- 층과 코드가 이미 채점한 설비는 L 근거로 쓸 수 없다. 같은 사실을 두 번 세지 않기 위해서다([backend/app/domain/report.py](../backend/app/domain/report.py)의 `rule_scored_space`).
- 1층·50㎡·설비 미입력이면 남는 근거가 면적 하나뿐이다.

따라서 "L 등급 차이 0"은 이 입력 조건에서 AI가 고를 여지가 없었다는 뜻에 가깝다. 근거가 여러 개인 조건에서 L이 흔들리는지는 이번에 재지 못했다.

### 3. 평가자 역할 예산 초과 1건

테헤란로 2번째에서 심사관 평가자는 자료를 크게 한 번 읽은 뒤(입력 약 2.1만 토큰), 다음 호출이 심사관 몫의 입력 한도 4만 토큰을 넘어 실패했다(`BUDGET_EXCEEDED`). 나머지 세 평가자는 끝났고, 보고서의 평가 완료율은 0.75로 표시됐다.
