# Examiner 전용 평가표 v0.3 — 문장·근거 대조

작성: 2026-10-20 · 개정: 2026-10-30(v0.3) · 브랜치: `feature/examiner-agent` · 상태: 시험장(examiner_eval) 조정용·확인용·큰 시험지 유료 측정 완료.

## 목적과 범위

보고서 문장이 근거와 맞는지 확인한다. 점수·순위·배지를 바꾸지 않고, decision의 반영 여부를 서버가 대조하지 않으며, 화면에 반영 결과를 따로 표시하지 않는다. examiner에만 쓰는 것은 persona·전용 패킷·query_raw 제외·기간 풀어 쓰기다. 제출 형식·서버 제출 검사·COMMON·다른 세 평가자의 지시문과 패킷은 그대로 둔다. 다만 측정 중 찾은 실패 원인을 고치느라 모든 역할에 영향을 주는 변경 세 가지가 들어갔다(아래 "다른 역할에도 영향을 주는 변경").

## 바꾼 이유 (2026-10-18 AI 포함 10곳 기록)

| 관찰 | 값 |
| --- | --- |
| 기존 패킷의 초안 문장·근거 | 10곳 모두 문장 0·fact 0 (2,570~2,856자) |
| AI 보고서 문장 중 fact 슬롯이 있는 문장 | 초안·최종 20건 311문장 중 0 |
| 첫 submit_review 거절 | 완료 9곳 모두. 거절 지적 32개 중 fact 없음 23·미확인 인용 7·숫자 2 |
| 공간 조회 | 읽기 27번 중 13번 |
| 지시문 항목 중 서버가 이미 막는 것 | unknown 이유(report.py), L의 D/C/S 중복(report.py) |
| query_raw 사용 | 0번 |

## 전용 패킷 (`backend/app/agentic/examiner.py`)

| 키 | 내용 |
| --- | --- |
| candidates | 상위 후보마다 code_points·B·H·coverage·badge·L_status, reasons·risks·confirmation_conditions 문장 조각 원문, 관측 fact_ids, score_items |
| score_items | 문항 D1~D4·C1·C4·S1~S4·L의 행 `[item,status,grade,points,fact_ids]`. fact_ids는 observed·citable만 남긴다 |
| facts | 근거 카드 행 `[fact_id,industry_code,source,metric,period,unit,spatial_scope_ref,value]`. observed·citable만 넣는다 |
| spatial_scopes | 카드가 참조하는 공간 범위 원문 |
| summary_segments·limitations_segments | 초안 요약·한계 문장 |
| omitted_fact_ids | 상한 때문에 카드에서 뺀 fact 별칭 |
| checks.uncited | 후보의 reasons·risks·confirmation_conditions 중 fact 슬롯이 없는 문장의 후보·칸·순번(요약·한계 칸은 넣지 않는다) |

- 카드 순서: 문장에 인용된 fact → 후보 fact_ids → 요약·한계 인용 → 문항 순서(D1부터 L)로 후보를 번갈아.
- 문장은 `.`·`?`·`!` 묶음에서 나눈다(`...`, `?!`는 한 번). 마침표 바로 뒤에 오는 fact 슬롯은 앞 문장의 근거로 본다.
- 상한 12,000자(checks 포함). 넘치면 뒤쪽 카드의 value부터 null로 바꾸고, 그래도 넘치면 뒤쪽 카드를 빼서 omitted_fact_ids에 남긴다. 출처·기간·범위는 카드가 남아 있는 한 지우지 않는다. 문장 조각과 score_items는 줄이지 않으며, 이것만으로 넘치면 평가 실패(SOURCE_UNAVAILABLE)다.
- 값 원문이 500자를 넘는 카드는 value를 null로 두고 get_facts로 읽게 한다.
- 별칭 변환 뒤 score_items·facts를 행으로 바꾼다. 키 반복을 없애 같은 카드 수를 담는다.
- examiner에게 보내는 자료(전용 패킷, 도구 응답, 모델 호출 메시지)에서만 기간 코드를 풀어 쓴다(`aliases.label_periods`). `20231~20234` → "2023년 1분기~4분기", `20224~20234` → "2022년 4분기~2023년 4분기". 저장값과 모델이 보내는 값은 바꾸지 않는다. 다섯 자리 분기 코드를 모델이 "여러 해"로 잘못 읽어 헛지적을 냈기 때문이다(v0.2).
- decision·founder·customer·landlord_advocate는 원래 분기 코드를 받는다(v0.3). 서버 숫자 검사(`app/text.py`)는 따로 선 분기 코드 `20231`은 통과시키지만 풀어 쓴 "2023년 1분기"는 숫자로 보고 거절한다. examiner persona에는 "기간은 말로 쓰라"는 안내가 있지만 다른 역할에는 없다.

| 변경 | 위치 | 영향 |
| --- | --- | --- |
| 모델 서버 연결이 끊기면 호출 예산 범위 안에서 한 번 다시 시도하고, 다시 시도한 호출도 예산에 센다 | `app/llm/client.py` | 모든 역할. 예산 범위 밖 호출은 그대로. decision 루프의 기존 연결 오류 재시도와 겹쳐 한 단계 최대 네 번 시도할 수 있다 |
| 평가자 답이 길이 상한에서 잘리면 짧게 다시 제출하라는 안내와 함께 제출 기회를 주고, 세 번째면 REPORT_INVALID로 끝낸다 | `app/agentic/evaluators.py` | 평가자 넷. 잘림도 제출 실패 횟수에 들어가 종료 이벤트의 rejections에 잡힌다 |

## 고정 평가표 — 네 칸

| 칸 | 보는 것 | 지적 |
| --- | --- | --- |
| 근거 | 문장에 fact 슬롯이 있는가 | 없으면 그 후보 score_items에서 문장을 뒷받침할 fact를 골라 target=claim, kind=missing_evidence |
| 출처 | 인용 fact의 source·metric이 문장 내용과 맞는가 | 어긋나면 scope_mismatch |
| 기간 범위 | fact의 period·spatial_scopes가 문장이 말하는 시점·범위와 맞는가 | 어긋나면 scope_mismatch |
| 중복 | 같은 원천 지표가 두 문항에서 함께 점수가 되어 같은 현상을 두 번 세는가 | target=score, kind=duplicate_score |

확인하지 못한 칸은 action_condition으로 남긴다. 공간·운영은 founder, 손님 수요는 customer, 임대 지속성은 landlord_advocate가 맡으므로 공간 초안 경고를 되풀이하지 않는다. unknown 이유와 L 중복 채점은 서버 검사에 맡긴다. persona에는 숫자를 넣지 않는다(지적 문장으로 옮겨 적어 거절되는 일을 막는다).

v0.2에서 persona에 더한 것:

- checks를 먼저 보고, 그 뒤에도 폐업률처럼 기간이 있는 문장은 이유·위험 칸을 가리지 않고 인용 fact의 출처·기간 범위 칸을 확인한다.
- 기간·범위가 실제로 다를 때만 scope_mismatch로 지적하고, 문장이 근거보다 덜 자세히 썼을 뿐이면 action_condition으로 남긴다.
- fact 슬롯이 있는데 엉뚱한 지표를 가리키면 근거 없음(missing_evidence)이 아니라 출처 틀림(scope_mismatch)으로 지적한다. 바꿔치기된 자료를 짚고도 근거 없음으로 붙이는 일이 많았다.
- comment·suggested_check에 숫자 문자가 하나라도 있으면 서버가 거절한다. 연도·분기, 값, 업종 코드, 문항 이름, fact_id 별칭에도 숫자가 섞여 있으니 옮겨 쓰지 않는다. 후보와 근거는 칸이 가리키므로 문장에서는 '이 후보', '인용 근거'로 쓰고, 기간은 '최근 한 해', '가장 이른 해', '관측 기간 전체'처럼 말로 쓴다. 거절된 뒤 다시 낼 때 모델이 맞는 지적까지 빼 버리는 일이 있었다.

## 도구

examiner는 get_scorecard·get_facts·submit_review만 받는다. 근거 값은 코드가 원자료에서 계산하므로 원자료 재대조는 테스트의 몫으로 두고, 출처·기간·범위 확인은 근거 카드로 한다. 다른 세 평가자는 query_raw를 그대로 쓴다.

## v0.2 측정 (시험장 `backend/examiner_eval`, 모델 gpt-6-luna)

오류를 심은 시험 초안(E1 근거 뺌·E2 다른 자료 붙임·E3 위험 문장에 가장 이른 해 폐업률 붙임), 오류 없는 초안, 실제 초안을 만들어 조정용 사례 12개로 고치고 확인용 사례 13개로 다시 쟀다. 각 3회 평균이다. 확인용 결과(V1은 v0.1 문구·패킷, V2는 v0.2):

| 항목 | V1 | V2 |
| --- | --- | --- |
| 실제 초안에서 근거 없는 후보 찾음 | 50% | 86% |
| E1 찾음 / 정확히 | 40% / 13% | 73% / 13% |
| E2 정확히 | 47% | 40% |
| E3 정확히 | 67% | 60% |
| 오류 없는 초안 헛지적(사례당) | 1.40 | 1.20 |
| 오류 심은 초안 헛지적(사례당) | 0.47 | 0.20 |
| 첫 제출 거절 | 46% | 10% |
| 심사 실패 | 17.9% | 15.4% |
| 사례당 호출 / 입력 토큰 | 2.69 / 26,306 | 1.56 / 13,907 |

- 심은 오류 종류마다 5건이라 한 건이 20%p다. 버전 사이 차이 대부분은 방향만 본다.
- 조정용에서 본 E1·E3 개선(정확 47%·93%)은 확인용에서 다시 나오지 않았다. V2가 확실히 나은 것은 실제 초안 찾기, 첫 제출 거절, 오류 심은 초안 헛지적, 비용이다.

## v0.3 측정 (큰 시험지 60곳)

확인용 13사례는 오류 없는 초안이 15건뿐이라 안내문 몇 줄에도 헛지적이 ±0.7씩 흔들렸다. 그래서 코드 채점만 된 백테스트 주소 60곳으로 시험지를 새로 만들었다(사례 120개: 오류 없는 초안 60, 오류 심은 초안 60, 심은 오류 178개). 3회 평균, 조정용·확인용 합산이다. 시험지가 달라 v0.2 표와 직접 비교하지 않는다.

| 항목 | 값 |
| --- | --- |
| E1 찾음 / 정확히 / 같은 원천으로 짚음 | 96% / 49% / 88% |
| E2 정확히 | 71% |
| E3 정확히 | 87% |
| 오류 없는 초안 헛지적(사례당) | 2.24 |
| 첫 제출 거절 | 11% |

## 측정 해석 주의 (v0.3)

- 2026-10-29 이전 V0·V1 측정은 기준선이 깨끗하지 않다. 기간 풀어 쓰기가 모든 역할에 적용되어 V0·V1도 풀어 쓴 기간을 받았고, persona에 "기간은 말로 쓰라"는 안내가 없어 숫자 거절이 늘었다. 그래서 V1 "첫 제출 거절 46%"의 일부는 이 브랜치가 만든 거절이다. 이후 V0·V1은 원래 분기 코드를 받는다.
- E1 "정확히"는 원래 문장에 붙어 있던 fact를 인용해야 센다. 빠진 fact가 점포 수(commercial_area/store_count)면 패킷에 그 카드가 없어 맞히기 어렵다. 그래서 같은 원천(source)의 그 후보 fact로 짚은 비율 `E1_source`도 함께 낸다.
- 실패한 사례는 "찾지 못함"이고 헛지적 0개로 계산된다. 버전마다 실패율이 다르면 헛지적 평균이 낮게 보이므로 실패를 뺀 평균 `clean_false_positives_done`도 함께 낸다.
- checks에는 근거 없는 문장(uncited)만 둔다. 같은 원천 지표를 쓰는 점수 문항 묶음(shared_sources)은 지표 이름이 문항마다 달라 늘 비어 있었고, 실제 입력 지표로 묶자 모든 후보에 S1·S4 중복 지적이 붙고 "S1·S4" 문항 이름 때문에 숫자 거절이 크게 늘어 뺐다(2026-10-30). 중복 칸 규칙 자체는 그대로다.
- 시험장은 실행 기록(`agentic_runs`)을 저장하지 않는다. `build`가 복사본 옆에 표식 파일(`*.examiner_eval`)을 남기고, 표식 없는 DB에는 실행하지 않는다. 결과 머리 행에 코드 버전(git HEAD, 고친 채 돌리면 `+수정중`)을 남기고, 코드가 바뀐 뒤 같은 폴더에 이어 돌리면 거절한다.

## 남은 위험과 다음 측정

- (v0.2) 심사 실패 15~18%는 대부분 제출 없이 끝남(SOURCE_UNAVAILABLE)이고 특정 주소에 몰려 있다. 원인을 아직 보지 않았다. → v0.3에서 원인(연결 끊김, 답 잘림, 한 번에 큰 근거 요청)을 고쳐 큰 시험지 실패 2%.
- (v0.2) 오류 없는 초안 헛지적이 사례당 1.2개 남는다. "최근 한 해"가 기준 시점을 밝히지 않는다는 지적, 폐업률 0인 문장을 위험 칸에 둔 데 대한 지적, 근거를 다른 지표로 착각한 지적이 섞여 있다.
- (v0.2) E1 "정확히"는 원래 뒷받침하던 fact를 인용해야만 세는 좁은 채점이다.

- 비측정 모드에서 examiner 역할 입력 한도 40,000은 읽기 단계에 적용된다. 첫 호출이 커졌으므로 읽기 세 번 중 한 번에 큰 응답(예: fact 서른두 개 조회)을 받으면 세 번째 읽기 전에 BUDGET_EXCEEDED로 실패할 수 있다. 측정 모드 실행은 이 한도를 검사하지 않으므로, 유료 측정 뒤 녹화의 호출별 입력으로 따로 확인한다.
- 유료 측정(같은 10곳 한 회, 허락 뒤 실행)에서 볼 지표: 첫 제출 거절 수, fact 없음 거절 수, 문장·근거를 짚은 지적 수, 공간·L 경고 반복 수, examiner 호출·입력, 실패 수. 한 번 측정이라 경향만 본다.
