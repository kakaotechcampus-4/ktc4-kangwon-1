# Founder 전용 평가표 v2 — 임차인·창업자 관점

## 현재 기준 — 2026-10-26

코드가 정한 공간 제외·순위 보정·점수·배지는 다시 판단하지 않는다. 임차인이 실제 운영 전에 확인할 조건과, **패킷으로 받은 운영·공사 관련 초안 문장**의 오류만 검토한다. 아래 v0.1은 이전 실행의 기록이다.

### 입력·근거·지적

- 후보 최대 다섯 개의 추천 이유·위험·확인 조건 문장 전체를 제공한다. 후보별 공간 판정은 참고용이며 인용 fact가 아니다.
- 사용자 확정값, 지속성·경쟁·현재 공간 비교의 관측 fact를 후보별로 배치한다. 결측은 0이 아니며 생략한 값은 읽기 도구로 확인한다.
- 공간 요건은 현재 검토된 표(`reviewed=true`, `confidence=low`)다. 면적은 운영 추정이며 법규·영업 가능성을 보증하지 않는다. 해당 없음·미확인을 불리하게 취급하지 않는다.
- 기본 지적은 `condition/action_condition`이다. 패킷에 실제 전달된 후보 문장의 운영·공사 주장과 관측 근거가 충돌할 때만 `claim/factual_error`를 허용한다. 해당 문장 내용을 짚어 설명한다. 본문이 없는 후보의 단정·누락은 주장하지 않는다.
- 원천·기간·공간 범위 오류, 근거 누락 일반론, 점수·L 재채점은 examiner에게 맡긴다. 다른 종류의 지적은 founder 제출에서 거절한다. 운영·공사라는 의미 경계의 준수는 실호출에서 별도로 검토한다.
- 같은 원인은 묶는다. 지적마다 관측·인용 가능한 fact를 최대 다섯 개 붙이고, 숫자는 문장 대신 fact로 인용한다. 기존 초안에 충분히 적힌 확인 행동은 반복하지 않는다.
- `agree`는 중요한 오류·확인 과제가 없을 때, `conditional`은 확인 과제 또는 자료 부족이 남을 때, `oppose`는 관측 근거로 핵심 운영 전제의 명백한 충돌이 있을 때만 사용한다. 자료 부족·낮은 점수만으로 반대하지 않는다.

### 패킷·예산

패킷은 12,000자 이내다. 모든 카드가 관측·인용 가능하다는 공통 조건은 `fact_defaults`에 한 번만 적는다. 출처·지표·기간·단위와 후보 문장은 유지한다. 개별 값의 500자 선제 생략은 하지 않는다.

그래도 넘으면 기타 근거 → 경쟁 → 지속성 → 공간 비교 순으로 값을 생략한다. 사용자 확정값은 그 뒤까지 보존한다. 낮은 우선순위의 값과 카드 메타데이터를 줄인 뒤에만 다음 우선순위로 넘어간다. 값 생략은 `read_required`, 카드 생략은 `omitted_fact_ids`로 남기며 근거 ID를 없애지 않는다. 문장·참조만으로 한도를 넘으면 실패를 알리고 조용히 잘라 보내지 않는다. fact 별칭은 기존 요청별 변환을 사용한다.

평가자 입력 예산은 누적 40,000토큰이며 패킷 글자 수와 다른 단위다. 읽기 최대 세 회·지적 최대 네 개 및 기존 제출 예산은 그대로 둔다. 초기 패킷과 도구 정의의 크기를 로컬에서 측정하되 실제 입력 토큰·읽기 기록은 승인된 실호출에서만 관찰한다.

### 실호출 판정 기준 — 승인 전

- 주소: 서울 마포구 와우산로 94. 시험 답변: 1층·약 40㎡·이전 일반 소매.
- 확인 화면 시험값: 주방 `installable`(설치 가능), 배기 `unavailable`(설치 불가), 급배수 `present`(있음). 실제 건물 상태라는 주장이 아닌 시험 입력이다.
- F3·F4 자료가 패킷에 공급됐는지, 별도 읽기를 했는지, 제출 내용에서 검토 흔적이 확인되는지를 각각 기록한다. 읽기 0회 자체를 미검토로 판정하지 않는다.
- 후보 문장 보존, 지적 수·거절 수·읽기 횟수, 공간 규칙과 중복된 지적 수, 초안 문장에 없는 주장·원천·기간·재채점 지적 여부를 기록한다.
- 패킷 글자 수, 입력·출력 토큰, 호출 수·시간과 decision 반영을 기록한다. 한 번의 관찰로만 보고하며 개선 확인이라고 표현하지 않는다. 승인 전에는 호출하지 않는다.

## 이전 기준·실행 기록 — v0.1

작성: 2026-10-19 · 브랜치: `feat/founder` · 상태: 사용자 승인 기준 반영·유료 실호출 한 회 관찰 완료. 결과는 [실행 기록](founder-live-report.md)에 있으며 일반적인 품질 개선을 확인한 것은 아니다.

## 목적과 범위

임차인이 추천 후보를 실제로 운영하기 전에 확인해야 할 조건을 근거와 함께 제시한다. decision의 D/C/S/L 점수·순위·배지를 다시 만들지 않는다. 별도 수치 점수표가 아니라 고정된 검토 항목과 verdict 기준이다. 다른 세 평가자·COMMON·도구·계약·예산은 변경하지 않는다.

현재 검토 패킷은 점수·L 요인·fact·한계를 전달하지만 후보별 추천 이유·위험·확인 조건의 본문은 전달하지 않는다. 따라서 초안이 무엇을 단정·누락했다고 추정하지 않는다. 이번 founder 지적은 모두 **target=condition, kind=action_condition**으로 제출한다. 본문 추가와 문장 오류 검증은 후속 과제다.

## 근거와 지적의 공통 규칙

- 해당 후보 또는 공통 조건의 `observed`이며 `citable=true`인 fact만 사용한다. 지적마다 실제 fact_ids를 한 개에서 다섯 개까지 붙인다.
- `space_requirements`의 observed는 초안 원문을 읽었다는 뜻이다. `space_fit`의 observed도 임대인 답변과 초안을 비교했다는 뜻이며, 검증된 법규·시설 기준이나 영업 적합성을 뜻하지 않는다.
- reviewed=false·낮은 confidence를 유지한다. 미확인과 해당 없음을 불리 요인으로 쓰지 않는다. 소매업의 주방·조리 배기 부재만으로 불리하게 판단하지 않는다.
- 근거 없는 지적을 만들지 않는다. 임대료·보증금·공사비·매출·마진·손익은 현재 fact 지표에 없으므로 임의로 추정하지 않는다.
- 같은 원인의 여러 업종은 하나로 묶는다. 최대 네 지적을 채우려 하지 않는다. 관측 근거 → 임차인에게 필요한 확인 → 확인할 상대·행동 순서로 짧게 쓴다.
- comment·suggested_check의 측정 숫자는 직접 쓰지 않고 fact_ids로 인용한다. 업종 코드 등의 식별자는 공통 has_digit 예외를 따르되, 검사 예외를 근거 없는 측정값 표기에 이용하지 않는다.

| F5 임차인이 입점 전 직접 확인할 순서 | F1~F4에서 사용한 관측 fact·명시된 임대인 답변 | 같은 조건을 반복하지 않고, 현장 배치·설비 상태 확인 → 임대인과 공사 허용·책임 범위 확인 → 필요 시 시공업체 견적·관할기관 확인 순서로 행동을 구체화. 현재 상황에 필요한 단계만 제시 | 모든 기관에 모두 확인하라는 일반론 금지. 법적 금지나 허가 필요를 추정하지 않음. 새로운 임대인 질문 도구나 외부 조회는 사용하지 않음 |

이번 패킷 범위에서 위 항목의 지적 분류는 모두 `condition/action_condition`이다. F5는 새로운 위험을 추가하는 항목이 아니라 F1~F4의 확인 행동을 순서로 정리하는 기준이다.

## 우선순위와 조회 절차

1. 패킷의 Top 5·L 요인·기존 fact를 먼저 읽는다. 실행을 막을 수 있는 확인된 운영 충돌과 설비·공사 전제부터 확인한다.
2. 공간 요건이 더 필요하면 **Top 5 중 관련 업종의 실제 industry_code**를 지정한다. 예: `get_facts(industry_code="G203", source="industry_profile", metrics=["space_requirements"], limit=32)`. 일반 fact 조회는 최대 32개이고, fact_ids 조회와 조건 필터는 섞지 않는다.
3. 다섯 업종을 각각 조회하라는 지시가 아니다. 패킷에 있는 근거를 재사용하고, 읽기 세 회 안에서 중요한 후보만 좁혀 조회한다. 동일 오류·동일 인자를 반복하지 않는다. 필요 시 get_scorecard 또는 query_raw도 같은 세 회 안에서 사용한다.
4. 새 점수·순위를 만들지 않고, 근거가 있는 조건만 최대 네 지적으로 제출한다. 오류 수정 제출은 기존 실행기의 추가 두 회 규칙을 따른다.

## verdict 기준

| 판정 | 기준 |
| --- | --- |
| agree | 필요한 자료를 읽고 확인 가능한 운영 전제에서 중요한 모순이나 추가 확인 과제를 찾지 못한 경우. issues가 비어 있어도 가능 |
| conditional | 확인해야 할 조건이 남거나, 조회 실패·근거 부족으로 판단을 마치지 못한 경우. 인용 가능한 근거가 없으면 지적을 지어내지 않고 issues=[]로 제출 |
| oppose | 관측된 근거로 예정 운영의 핵심 전제를 충족할 수 없다는 명백한 충돌이 확인된 경우. 임대인 답변의 명시적 제한 등 확정 근거가 필요하며, 공간 요건 초안·미확인·낮은 코드 점수만으로 반대하지 않음 |

issues=[]는 agree를 자동으로 뜻하지 않는다. 모든 verdict는 검토 가능한 운영 전제에 대한 의견이며, 보고서 문장 단정의 유무나 점수 변경을 의미하지 않는다.

## 현재 현상과 후속 과제

- 이전 성공 실테스트에서 founder는 공간 요건 일반 조회에 limit=51을 두 번 사용해 INVALID_ARGUMENT를 받았다. COMMON에는 일반 조회 32개 상한이 없고 tool schema의 limit 최대는 space_fit 예외 때문에 51이다. 이 불일치가 재발할 여지가 있어 founder 문장에만 구체화한다.
- 같은 저장 실행의 get_facts를 읽기 전용으로 확인했다. founder 세 회 중 limit=51 오류 두 회, landlord_advocate 세 회·customer 세 회·examiner 두 회에는 같은 오류가 없었다. 따라서 공통 설명의 빈틈은 있지만 관측된 낭비를 네 평가자 공통 현상으로 단정하지 않는다. COMMON·계약은 변경하지 않는다.
- 후보 본문이 없으므로 기존 보고서의 주장 오류·이미 반영된 확인 조건과의 중복을 완전히 검증할 수 없다. founder에 한정한 초안 본문 전달은 후속 설계 과제다.
- agentic-decision-plan.md의 fact_ids≤3과 코드는 최대 5개로 다르다. prompt-change-notes.md의 과거 상위 열 업종 설명도 현 구조와 다르다. 기존 내용은 이번 변경에서 수정하지 않는다.
- founder persona는 85자에서 695자로 변경했고 COMMON은 493자로 유지한다. 패킷 12,000자 제한은 user 메시지의 패킷 자체에만 적용되므로 persona 증가가 이 한도를 차감하지 않는다. 대신 매 호출의 시스템 입력·전체 토큰은 증가한다. 새 실제 토큰은 실호출 전이라 미측정이다.

## 실호출 관찰 계획 — 한 회 승인됨

주소는 서울 마포구 와우산로 94, 시험 답변은 기존과 같은 층·면적·공간 상태를 사용한다. 기존 녹화를 덮어쓰지 않는다. founder만 이번 프롬프트를 사용하고 나머지 역할·코드 채점·설정은 유지한다. 승인 요청에서 알린 대로 새 호출 상한을 만들거나 기존 런타임 예산을 변경하지 않는다. 이전 실측과 같은 measurement=True 실행 경로를 사용한다. 결과는 founder-live-report.md에 기록한다.
