# 멀티에이전트 구현 기록

기준: `feature/mvp-1.5-orchestra`, `d2c4571`. 기존 P0 판정 지시문 수정 위에서 작업했습니다.
설계: [multi-agent-design.md](multi-agent-design.md), [순차 구현 계획](archive/superpowers/plans/2026-09-29-multi-agent.md).
실행 방법과 한도는 [backend/README.md](../backend/README.md)의 "실행 모드"·"한도"가 기준입니다.

## 반영한 내용

- 추가형 전문가 계약·공용 근거 검증·75개 업종 축약 입력.
- 공통 전문가 실행기, 역할별 LLM 설정, 요청별 모델 호출 예산 24회(마지막 2회는 최종판단·교정 몫).
- 기존 읽기·보완·지도 도구를 오케스트레이션에서 연결. 계산·공간 범위는 유지.
- 브리핑 → 최종판단 → 선택적 되묻기(2라운드)·임대인 질문(1회).
- 브리핑·답변·지도 차수 이력, v1/v2 질문 재개, 소비 예산·활성 시간 복원.
- 선택형 GET `deliberation`, 네트워크 없는 전체 흐름 시험, 로컬 검증 도구 trace.

기본은 `single_decision`입니다. 커밋·푸시는 하지 않았습니다.

## 구현 중 결정

| 항목 | 선택과 이유 | 한계 |
| --- | --- | --- |
| 작업 위치 | 사용자 지정 작업 트리에서 P0 변경을 보존 | 별도 worktree 격리 대신 diff 대조 |
| 지도 알림 | `on_map_result(observation, adopted)` 추가, 기존 콜백 유지 | 이력 저장과 최종 채택을 구분해야 함 |
| 예산 | 비동기 예약을 DB 저장한 뒤 모델 전송 | 예약마다 짧은 SQLite 지연 발생 |
| 근거 검증 | 경로·업종·직접 숫자·지원 단위만 검증 | 문장 의미의 진실성은 사람 평가 필요 |
| 지도 매핑 | 예산 저장 오류만 기존 fallback에서 제외 | 새 저장 실패를 모델 실패로 숨기지 않기 위한 예외 경계 변경 |
| trace | 기존 `trace.py`에도 새 행동·도구 이름만 추가 | 계획의 run.py 변경만으로는 새 행동이 final로 표시됨 |

## 최종 리뷰에서 보완한 경계

| 문제 | 반영 |
| --- | --- |
| 새 지도 검색은 성공했지만 업종 매핑이 퇴행 | 기존 확정 장소·업종을 잃는 관측은 미채택 |
| 100m·500m 점포 수를 축약하면서 개별 반경 누락 | 축약 지표와 반경 조회 도구에 해당 반경·원본 경로 보존 |
| 미채택 지도 조회가 누적 5개 제한에서 빠짐 | 채택 여부와 별도로 시도한 대상 유지, 저장 계획 전체에서 재개 시 복원 |

## 실측과 수정 (2026-09-29)

실제 모델·API로 돌려 보니 대역 시험에서 보이지 않던 문제가 나왔습니다. 발견한 순서대로 고쳤습니다.

| 발견 | 원인 | 수정 |
| --- | --- | --- |
| 되물은 전문가 3명 모두 답변 `unavailable` | 호출 예산 12회가 되묻기 1라운드에서 바닥남. 도구만 쓰고 정리(`finish`) 차례가 없음 | 예산 24회(`MAX_CALLS`). 되묻기 전에 남은 호출을 전문가 수로 나눠 배정하고 마지막 차례는 `finish`만 허용. 지도 전문가는 매핑 호출을 감안해 차례를 적게 배정 |
| 지도 검색 0건 | 검색어로 공식 업종명("세탁업")을 씀 | 전문가 지시문·도구 설명에 일상어 검색어 규칙("세탁소") 추가, 0건이면 다른 말로 한 번 더 |
| 판정 교정 원인이 남지 않음 | 교정이 성공하면 실패 기록을 저장하지 않음 | 검증 도구 trace에 교정 사유·위치·업종 기록(모델 원문 경로는 기록하지 않음) |
| 브리핑 3개 모두 대체 요약(fallback) | ① 배열 번호를 잘못 셈(한식을 말하며 중식 행 경로) ② 근거 4개 이상인 주장 하나가 브리핑 전체를 무효화 ③ "반경 2,000m", "12개 분기", "10대" 같은 문맥 숫자를 틀린 숫자로 판정 | ① 전문가에게 업종별 경로·값 목록(`industry_paths`) 제공 ② 형식이 틀린 주장만 제외 ③ 원자료의 반경과 기간·연령대·시간대 표현은 문맥으로 허용. 직접 셈한 숫자(개업−폐업 차이 등)는 계속 거절 |
| 3.0 첫 시도 6회 중 3회 요청 전체 실패 | 판정관이 같은 전문가에게 질문 2개를 보내 `ConsultPlan` 형식 오류 | 같은 전문가의 첫 질문만 남기고, 허용되지 않은 전문가 질문은 제외. 남는 질문이 없을 때만 오류 |

판정 지시문도 멀티에이전트 입력(`industry_digest`·`neighborhood`·`briefs`·`answers`·`limits`) 읽는 법,
근거 짝 복사 규칙, 전문가별 확인 가능한 도구, 전문가 먼저·임대인은 공간 조건만이라는 순서를 추가했습니다.
"반드시 물을 필요는 없습니다"처럼 도구 사용을 억누르던 문구는 뺐습니다.

### 비교 측정

반경 500m, 지도 포함, 같은 모델, 임대인 질문 비활성, 주소 3곳 각 1회 순차 실행입니다.
multi_agent는 위 수정을 모두 반영한 뒤의 실행입니다.

| 주소 | single_decision | multi_agent | 모델 호출 | multi_agent가 한 일 |
| --- | --- | --- | --- | --- |
| 송파 오금로 404 | 45.0초 (`266682fa`) | 104.1초 (`50548eb1`) | 2 → 15 | 전문가 3명 되묻기, 도구 4회, 교정 1회 |
| 강남 테헤란로 123 | 79.6초 (`32d3e2c8`) | 75.1초 (`abc5a942`) | 3 → 12 | 지도 전문가 1명, 검색 3회 |
| 성동 아차산로 83 | 40.1초 (`19655c43`) | 76.7초 (`efc80d9c`) | 1 → 12 | 전문가 3명 되묻기, 도구 3회 |

- 3곳 모두 판정관이 전문가에게 되물었고, 브리핑 3개를 모두 모델이 작성했습니다.
- 평균 54.9초 → 85.3초, **1.55배**입니다. 도입 조건(1.5배 이내)을 근소하게 넘었습니다.
- 한계 문장이 17개 안팎에서 35~45개로 늘었습니다. 확인하지 못한 점을 더 밝히지만 읽을 양도 늘었습니다.
- 추천이 크게 달라진 주소가 있습니다. 강남은 의원(Q102), 성동은 간이음식(I210)·M103이 2.0 추천에서 3.0 비추천으로 바뀌었습니다.
  어느 쪽이 맞는지는 이 측정으로 알 수 없어 팀 블라인드 평가로 판단합니다.
- 한 번씩만 측정했으므로 속도·품질 우세를 단정하지 않습니다.

## 검증 기록

- 기준선: Python 3.12.14, 백엔드 486개 통과.
- 구현 완료 시점: 백엔드 540개, 검증 도구 31개 통과.
- 실측 수정 반영 후: 백엔드 544개 통과. Ruff·포맷·mypy(84개 소스) 통과, 검증 도구 테스트 통과.
- 새 시험: 마지막 차례 `finish` 강제·차례 배정, 문맥 숫자 허용과 셈한 숫자 거절, 겹친 전문가 질문 처리.

테스트는 대역 회귀이며 서비스 응답 속도·추천 품질을 보증하지 않습니다.

## 실행

루트에서 외부 호출 없이 지도 되묻기·질문 대기까지 확인:

```powershell
conda activate chaeum
python validation_tool/run.py --offline-multi --radius-m 300
python validation_tool/run.py --resume "validation_tool/runs/출력된요청ID" --skip-questions
```

실제 모드는 `backend/.env`에 `ANALYSIS_MODE=multi_agent`를 설정하고 서버를 재시작합니다.
검증 도구는 Git 제외 대상입니다. 팀 공유용 대역 검증은 `backend/tests/test_multi_agent_flow.py`에 있습니다.
