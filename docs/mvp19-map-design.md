# MVP1.9 카카오맵 보완 조회 설계

작성일: 2026-09-28

기준: `feature/mvp-1.5-orchestra` / `e8b5246`

조회 도구 원본: `origin/feature/map-analysis-agent` / `daa3f14`
상태: 설계 검토용. 아래 연결 기능은 아직 구현하지 않음.

## 1. 목적과 책임

임대인에게 업종 후보를 제시할 때, 최종판단이 필요하다고 판단한 주변 업종과 교통·시설 정보를 카카오맵으로 추가 확인한다. 분기 통계와 조회 시점의 지도 등록 정보를 구분한다. 실제 영업 여부·입점 가능성·법적 적합성을 보증하지 않는다.

- 최종판단: 확인할 업종·시설, 필요한 이유, 추천에 미치는 영향을 요청한다.
- 오케스트레이터: 요청 검증, 좌표·반경 고정, 호출 제한, 조회 실행, 저장을 담당한다.
- 지도 도구: 검색·중복 제거·업종 매핑·관측 결과를 반환한다. 업종 추천은 하지 않는다.
- 기존 세 분석 에이전트와 `AgentId`는 그대로 유지한다. 지도는 네 번째 필수 분석이 아니다.

## 2. 흐름과 호출 제한

```text
주소 준비 → 세 분석 → 최종판단
                       ├─ 최종 결과
                       ├─ 기존 분석 보완 → 최종판단
                       ├─ 지도 조회·매핑 → 최종판단
                       └─ 임대인 질문 → 저장·대기 → 답변 → 최종판단
```

- 지도는 명시적으로 도구를 주입한 실행에서만 사용한다. 미등록이면 모델에 요청 선택지를 제공하지 않는다.
- 기존 보완 최대 1라운드와 별도로 지도 조회는 최대 1배치, 검색 요청 1~5개다. 실패해도 배치를 소비한다.
- 지도와 기존 보완 중 필요한 것을 먼저 선택할 수 있으나, 각 단계가 끝나면 최종판단으로 돌아온다. 두 종류를 한 모델 응답으로 동시 요청하지 않는다.
- 질문은 기존대로 최대 3개·1회다. 질문을 먼저 선택했다면 답변 후 지도·보완을 새로 실행하지 않는다.
- 좌표·반경은 `AnalysisTask`에서만 주입한다. 모델이 좌표·반경·API URL을 지정하지 못한다.
- 도구가 지원하지 않는 반경은 명시적 실패로 남긴다. 조용히 축소하지 않는다.
- HTTP 재시도·동시 요청 제한은 원본 클라이언트를 재사용한다. 그래프의 반복 예산은 새 분기를 포함해 유한하게 검증한다.

## 3. 조회 요청과 검색

공통 계약에 `MapLookupPlan(action="map_lookup")`을 추가한다. 각 요청은 다음 두 종류 중 하나다.

| 종류 | 입력 | 처리 |
| --- | --- | --- |
| 업종 | 공통 75개 중분류 코드, 검색 표현, 이유·판단 영향 | 코드는 공통 마스터로 검증, 검색 표현은 지도 검색용으로 사용 |
| 인프라 | 지원 시설 코드, 이유·판단 영향 | 코드가 정한 카카오 카테고리로 조회 |

검색 표현은 최대 50자이며 주소를 덧붙이지 않는다. 요청마다 코드가 query ID를 부여하고 동일 종류·대상·검색 표현은 중복 제거한다. 업종명은 마스터에서 채우며 LLM의 명칭을 신뢰하지 않는다.

검색 표현은 검색 범위를 결정할 뿐 결과의 업종을 확정하지 않는다. `카페`로 검색한 모든 장소를 I212로 자동 배정하지 않는다.

인프라는 원본 도구가 지원하는 시설 분류를 사용한다. 학교급별 조회가 아니라 전체 학교 조회라면 실제 적용 분류를 그대로 보여준다. 버스 노선·배차·도보 이동시간 조회는 이번 범위 밖이다.

## 4. 장소별 75개 업종 매핑

기존 공통 마스터와 조회 함수를 재사용한다. 별도 75개 목록을 복제하지 않는다.

1. 검색마다 반환된 장소 ID·이름·원본 분류·거리·URL을 보존한다.
2. 업종 조회 결과는 장소 ID 기준으로 배치 내 중복 제거한다. 각 검색과 장소의 연결은 유지한다.
3. 고유한 원본 카테고리 경로를 모아 기존 공통 LLM 호출 계층으로 한 번에 매핑한다. 이미 제공된 원본 카테고리 코드도 함께 전달한다.
4. 응답은 원본 카테고리별 `mapped / ambiguous / unmapped`와 75개 중 하나의 코드 또는 null, 간단한 이유를 반환한다. 코드 포함 여부·중복·입력 범위를 검증한다.
5. 명칭·대분류는 코드로 채운다. 매핑 방법은 `llm`으로 기록하고 사람 검수된 확정표처럼 표현하지 않는다.
6. 매핑 불가·애매함은 강제로 배정하지 않는다. 매핑 실패 시 원본 장소를 유지하고 업종 집계만 미완료로 표시한다.

인프라 요청 결과는 시설 자료로 유지하며 75개 업종에 억지로 매핑하지 않는다. 같은 장소가 업종·시설 조회 모두에 등장하면 조회 목적은 각각 보존하되 업종 표본 집계에서 중복 가산하지 않는다.

별도 자율 매핑 에이전트나 영속 매핑 캐시는 만들지 않는다. 지도 매핑용 모델 설정은 기존 설정 구조를 재사용해 별도 모델 선택이 가능하도록 하고, 네트워크 호출 없이 함수 주입으로 시험한다.

## 5. 관측 결과와 해석 한계

지도 관측에는 요청 ID·관측 ID·좌표·반경·UTC 조회 시각·마스터 버전·상태·경고를 기록한다.

- 검색별: 요청 대상, 실제 검색 표현·방식·카테고리, API 검색 건수, 반환 장소 ID 목록, 오류.
- 장소별: 원본 분류, 장소 ID, 거리·URL, 매핑 상태·코드·방법·이유.
- 업종별: 중복 제거한 조회 표본의 매핑 건수. 전체 점포 수나 밀도로 표현하지 않는다.
- 시설별: 검색 결과와 조회 표본 내 가까운 장소. 거리에서 도보 시간·접근성을 임의 계산하지 않는다.

첫 연결에서는 원본의 검색당 첫 페이지 최대 15건을 유지한다. 표본임과 추가 결과 존재 여부를 표시하며 전수 수집 기능을 추가하지 않는다.

조회 실패와 정상 0건은 분리한다. 실패한 검색의 건수는 null이다. `matched / sampled`는 분류 문자열 일치 참고치이며 통계적 신뢰도나 전체 건수 보정 비율이 아니다. 브랜드 수도 표본 자료다.

일부 검색·매핑 실패는 partial, 전부 조회 실패는 error, 정상 조회 결과가 모두 0건이면 no_data로 남긴다. 지도 실패만으로 기존 분석을 폐기하지 않는다. 잘못된 계약·ID나 저장 실패는 기존 정책대로 실행 오류로 전파한다.

## 6. 최종판단 계약과 근거

- 공통 `schemas.py`에 지도 요청·관측 계약을 둔다. 외부 응답 해석 모델은 지도 폴더에 둔다.
- 기존 `DecisionRequest.analyses`와 `DecisionResult.source_analyses`는 세 분석 전용으로 유지한다.
- 입력·출력에 선택형 `map_observation`을 추가한다. 기존 기록은 필드가 없어도 읽을 수 있어야 한다.
- `Evidence.agent_id`에만 지도 출처 `map_analysis`를 추가한다. 분석 실행용 `AgentId`에는 추가하지 않는다.
- 지도 근거 경로는 관측의 `data` 내부를 기준으로 검증한다. 오류·매핑 미확정 자료를 특정 업종의 확정 근거로 사용할 수 없다. 정상 조회 0건 자체는 근거로 허용한다.
- 최종 결과에 포함되는 지도 관측은 모델이 생성하지 않고 코드가 원본을 붙인다.
- 코드가 원본 통계와 지도 건수를 합산하지 않으며 프롬프트에서도 금지한다. 조회 범위·시점·표본 차이를 함께 설명한다.
- 기존 세 분석이 전부 없는 경우 지도만으로 업종 추천을 만들지 않는다. no_data 단축 경로를 유지한다.
- 필드 추가와 근거 출처 확장은 공통 계약 PR 검토 대상으로 명시한다. 이번에 프론트나 HTTP를 수정하지 않는다.

## 7. 저장과 질문 후 재개

기존 세 분석의 실행 차수와 분리해 `map_observations` 테이블 하나를 추가한다. 요청당 하나의 행으로 지도 요청, running/completed 상태, 관측 JSON, 시작·완료 시각을 저장한다. 관측 내부 상태와 실행 상태는 구분한다.

- 외부 조회 전에 요청·running을 저장하고, 조회·매핑 후 관측과 completed를 원자적으로 저장한다.
- 성공·부분 성공·조회 실패 모두 관측으로 남긴다. 키·원문 외부 오류는 저장하지 않는다.
- 최종 저장 시 DB의 지도 관측과 결과에 붙인 관측의 일치를 확인한다.
- 질문 대기 전에 관측 저장을 완료한다. 재개 시 같은 요청의 완료된 지도 관측을 읽고 모델에 다시 전달한다.
- 지도 미사용·기존 질문 기록은 관측 없이 재개한다. 중복 재개가 지도 호출을 일으키지 않아야 한다.
- 실행 중 강제 종료 자동 복구·재조회는 이번 범위 밖이다.

## 8. 가져올 범위와 구현 순서

원본 `91f8918`, `1800cc5`, `daa3f14`의 지도 관련 파일·테스트·예제만 반영한다. 원격 브랜치 전체 병합과 프론트·기존 DB 변경 반영은 제외한다.

1. 지도 도구 도입 및 원본 대역 테스트 확인.
2. 원본 장소 보존·입력 경계·표본 표시·75개 매핑 구현.
3. 지도 요청·관측·근거 계약과 최종판단 출력 파싱 연결.
4. LangGraph 선택적 조회 노드·호출 제한·실패 처리 연결.
5. DB·서비스·질문 재개와 trace 연결.
6. 회귀 검사와 사용자 실행 안내.

## 9. 완료 기준

- 질문·지도 미사용 실행의 기존 동작 보존.
- 같은 좌표·반경 전달, 5개 초과·잘못된 업종 코드·시설 코드 사전 거절.
- 검색 결과의 다른 업종, 장소 중복, 애매한 매핑, 마스터 밖 코드, 정상 0건·실패 구분 검증.
- 지도와 기존 보완 각각 한 번 제한, 질문 후 지도 재호출 금지.
- 근거 경로 및 업종 코드 검증, 지도 실패 시 정상 분석 보존.
- 저장 후 다른 프로세스에서 질문 답변을 재개해 동일 지도 근거로 최종판단 완료.
- 대역 API·매핑 LLM·판단 LLM으로 전체 흐름 검증. 실제 외부 호출은 별도 확인 후 진행.
- Python 3.12 unittest·Ruff·타입 검사. 커밋·푸시는 별도 요청 시 수행.
