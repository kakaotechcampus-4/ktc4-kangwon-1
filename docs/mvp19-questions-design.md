# MVP1.9 · 임대인 선택적 질문·재개 설계

작성일: 2026-09-28  
구현 기준: `feature/mvp-1.5-orchestra` · `b835ef9`  
상태: 구현·대역 검증 완료. 실제 LLM 질문 품질과 HTTP 연결은 별도 검증 대상이다. [진행 기록](mvp19-questions-progress.md)

## 1. 목표

주변 분석만으로 판단하기 어려운 경우, 임대인이 답할 수 있는 중요한 정보만 질문한다. 답변 후에는 기존 분석을 재사용해 최종판단을 이어간다.

질문은 필수가 아니다. 빈 필드나 `partial` 상태만으로 질문하지 않는다. 해당 정보가 추천 후보·순위·판단 보류에 어떤 영향을 주는지 설명할 수 있어야 한다.

## 2. 합의한 범위

- 질문 항목은 코드로 제한한다. LLM은 항목 선택·질문 문장·필요한 이유를 작성한다.
- 요청 하나당 질문은 한 번, 최대 3개다. 이미 받은 정보는 다시 묻지 않는다.
- 일부 답변, 모름, 건너뛰기를 허용한다. 답변 제출 후 재질문하지 않는다.
- 사용자 답변은 API 관측값과 분리한다. 법적 적합성이나 실제 입점 가능성이 검증됐다고 취급하지 않는다.
- 주소·반경 변경은 새로운 분석 요청으로 처리한다.
- 서비스·저장소·그래프·검증 도구까지만 연결한다. HTTP API·프론트엔드·건축물·법률 연계는 제외한다.
- 세 분석 에이전트의 분석 로직은 변경하지 않는다. 개폐업은 폴리곤 기준을 유지한다.

## 3. 현재 구현과 변경점

| 구간 | 현재 | 변경 설계 |
| --- | --- | --- |
| 최종판단 | 최종 결과 또는 데이터 보완 요청 | 사용자 질문 분기 추가 |
| 그래프 | 메모리 상태로 실행 후 종료 | 질문 대기 시 재개에 필요한 상태 보관 |
| 서비스 반환 | `DecisionResult` | 질문을 허용한 실행에서만 대기 결과도 반환 |
| 요청 상태 | pending / running / completed / failed | waiting_for_input 추가 |
| 저장 | 분석·보완 이력·최종 결과 | 질문·답변·재개 상태 추가 |
| 검증 도구 | 실행 결과·실패·보완 추적 | 질문 표시·답변 제출·재개 추적 추가 |

기존 호출은 질문 비활성 상태를 기본으로 유지한다. 질문 기능을 켠 서비스·검증 도구만 새 반환 형태를 처리한다. 기존 HTTP 경로가 질문 대기 결과를 받도록 자동 변경하지 않는다.

## 4. 판단과 실행 책임

| 최종판단의 선택 | 조건 | 오케스트레이터 동작 |
| --- | --- | --- |
| 최종 결과 | 확보한 근거로 판단 가능 | 검증 후 최종 저장 |
| 데이터 보완 | 결정에 중요하고 등록된 분석 도구로 확보 가능 | 허용된 작업만 선택적으로 실행 |
| 사용자 질문 | 결정에 중요하고 임대인이 답할 수 있음 | 질문 검증·저장 후 대기 |

LLM이 필요성을 판단하고, 코드는 허용 항목·횟수·중복·상태 전이를 통제한다. 확보할 방법이 없는 정보는 반복 요청하지 않고 한계로 남긴다.

```text
주소 준비 → 세 분석 병렬 실행 → 최종판단
                               ├─ 충분함 → 최종 결과 저장
                               ├─ 자료 보완 → 선택적 작업 → 최종판단
                               └─ 임대인 질문 → 저장·대기
                                                  ↓
                                          답변 / 건너뛰기
                                                  ↓
                                      기존 분석 + 답변으로 판단
                                                  ↓
                                            최종 결과 저장
```

데이터 보완은 기존처럼 최대 1라운드다. 첫 판단 또는 보완 후 판단에서 질문할 수 있다. 이번 단계에서는 답변 후 판단을 종료 판단으로 제한한다. 질문·추가 데이터 보완은 더 요청하지 않는다. 미확인 조건은 한계로 표시하고 판단이 불가능하면 `no_data`로 반환한다.

## 5. 질문·답변 계약

초기 허용 항목은 다음과 같다. 항목 코드는 고정하고, 질문 문장은 상황에 맞게 작성한다.

| 항목 코드 | 내용 | 답변 예 |
| --- | --- | --- |
| floor | 해당 공간의 층수 | 지상 2층 |
| exclusive_area | 전용면적 | 66㎡ |
| space_condition | 현재 공실 여부·이전 사용 업종 | 공실, 이전에는 사무실 |
| existing_facilities | 임대인이 알고 있는 기존 시설 | 급배수 있음, 배기 시설은 모름 |
| industry_preferences | 희망·제외 업종 | 음식점 제외 희망 |

질문 묶음에는 코드가 생성한 `request_id`, `question_set_id`와 질문 목록을 넣는다. 개별 질문에는 항목 코드, 질문 문장, 필요한 이유, 답변이 판단에 미치는 영향을 기록한다. 동일 항목은 중복 선택할 수 없다.

답변 제출에는 같은 요청·질문 묶음 ID와 항목별 `answered`, `unknown`, `skipped` 상태를 사용한다. `answered`만 비어 있지 않은 답변 문자열을 요구한다. 부분 제출 시 빠진 항목은 건너뛴 것으로 확정하며 임시 저장은 지원하지 않는다.

- 질문에 없는 항목·중복 항목·다른 요청의 질문 ID는 거절한다.
- 답변은 항목당 최대 1,000자로 제한한다. 숫자·시설 존재 여부로 임의 변환하지 않고 원문을 보관한다.
- 입력 주소 등 이미 확보된 문맥도 모델에 전달한다. 명시적으로 확보한 동일 항목은 코드에서도 질문 후보에서 제외한다.
- 답변은 지시문이 아닌 사용자 자료로 전달한다. 답변으로 도구 제한·요청 ID·주소·반경을 변경할 수 없다.
- 기존 `evidence`에는 실제 분석 경로만 사용한다. 사용자 답변을 분석 에이전트의 관측값처럼 인용하지 않는다. 판단 문장에는 사용자 제공 정보임을 구분한다.

최종 결과는 기존 `DecisionResult`를 유지한다. 대기 결과는 별도 계약으로 `status="waiting_for_input"`, 요청 ID, 질문 묶음을 반환한다. 미완성 판단을 최종 결과 형태로 위장하지 않는다.

## 6. 저장·재개 방식

검토안은 **질문 경계에서만 필요한 상태를 SQLite에 저장하고, 새 실행에서 판단 노드로 진입하는 방식**이다. 임의 노드 재개가 아니라 질문 재개만 지원하므로 별도 체크포인트 의존성 없이 기존 저장소를 재사용한다.

| 대안 | 선택 이유 |
| --- | --- |
| 질문 경계의 상태 저장·판단 노드 재진입 | 이번 범위에 필요한 상태만 관리. 기존 SQLite 트랜잭션 재사용 |
| LangGraph 전용 체크포인터·중단 기능 | 임의 노드의 장애 복구까지 필요할 때 검토. 이번 설계에서는 도입하지 않음 |

이 방식은 LangGraph의 네이티브 `interrupt` 구현이라고 부르지 않는다. LangGraph는 분기와 실행을 담당하고, 서비스·저장소가 질문 경계의 영속성을 담당한다.

새 질문 기록은 요청당 하나로 제한한다. 질문 묶음, 답변, 준비된 작업, 채택된 분석의 실행 차수, 보완 사용 여부·피드백, 상태 버전을 보관한다. 분석 본문은 기존 `agent_results`를 참조하고, 재개 시 동일 차수의 결과를 복원·검증한다. 함수·클라이언트·API 키는 저장하지 않는다.

```text
pending → running → completed
                 ├─ failed
                 └─ waiting_for_input → running → completed / failed
```

- 질문 기록 생성과 `waiting_for_input` 전환은 하나의 트랜잭션이다.
- 대기 중에는 `result_json`, `error_json`, `completed_at`을 비워 둔다. `decision_results`도 추가하지 않는다.
- 기존 `supplement_request_json`을 사용자 질문 저장용으로 재사용하지 않는다.
- 답변 저장과 `waiting_for_input → running` 전환도 하나의 트랜잭션이다. 조건부 상태 갱신에 성공한 실행만 모델을 호출한다.
- 같은 답변을 재제출하면 실행 중에는 실행 중임을 알리고, 완료 후에는 저장된 결과를 반환한다. 확정한 답변과 다른 내용의 재제출은 거절한다.
- 재개는 최종판단부터 시작한다. 주소 변환·분석·이미 수행한 보완·개별 분석 저장 콜백을 반복하지 않는다.
- 재개 실패 시 질문·답변·분석 이력을 보존하고 실패를 기록한다. 자동 재시도는 하지 않는다.
- 대기 시간은 실행 타임아웃에서 제외한다. 재개 호출에는 별도의 실행 제한시간을 적용한다.
- 대기 상태에서 프로세스를 종료해도 새 프로세스가 답변을 제출해 이어갈 수 있어야 한다. 실행 중 강제 종료의 자동 복구는 이번 범위에서 제외한다.

기존 SQLite 파일에는 상태 제약조건 변경을 위한 명시적 마이그레이션이 필요하다. 기존 요청·분석·판단 이력은 보존하며, 초기화 반복 실행으로 데이터가 사라지면 안 된다.

| `backend/app/agents/decision/agent.py`, 관련 프롬프트 | 질문 선택과 결과 검증, 사용자 정보 해석 |

구체적인 함수명과 파일 분리는 구현 계획에서 현재 함수 재사용 여부를 확인해 정한다. 별도 질문 에이전트는 만들지 않는다. 공통 계약 변경은 팀 공유·PR 검토 대상으로 명시한다.

## 8. 검증·완료 조건

Python 3.12와 기존 테스트 환경에서 외부 API·LLM 대역으로 먼저 검증한다.

1. 질문이 필요 없으면 기존과 동일하게 완료한다. `partial`만으로 질문하지 않는다.
2. 허용되지 않은 항목·중복 항목·4개 이상 질문·재질문을 차단한다.
3. 질문 후 DB를 닫고 다시 열어 같은 질문·분석 이력을 조회할 수 있다.
4. 새 프로세스에서 답변·부분 답변·모름·전체 건너뛰기로 재개할 수 있다.
5. 재개 시 주소·세 분석·기존 보완의 호출 횟수가 증가하지 않는다.
6. 보완 후 질문해도 채택된 분석과 사용한 보완 횟수가 유지된다.
7. 동시 답변 제출·중복 제출에도 모델 실행과 최종 저장이 중복되지 않는다.
8. 다른 요청의 답변·잘못된 ID·답변 길이 초과는 저장·실행 전에 거절한다.
9. 질문 저장 실패·재개 모델 실패·최종 저장 실패를 성공으로 처리하지 않는다.
10. 기존 분석·서비스·DB 테스트와 질문 비활성 HTTP 경로를 회귀 검증한다.

`validation_tool`에서는 질문 생성, 대기 저장, 답변 접수, 판단 재개, 최종 저장을 구분해 남긴다. 실제 모델의 질문 필요성은 별도 사례 평가로 확인하며, 대역 테스트 통과를 실제 판단 품질 검증으로 표현하지 않는다.

완료 기준은 **필요할 때만 질문하고, 실행을 종료했다가 답변으로 재개해, 기존 분석을 반복하지 않고 최종 결과와 질문·답변 이력을 조회할 수 있는 것**이다.
