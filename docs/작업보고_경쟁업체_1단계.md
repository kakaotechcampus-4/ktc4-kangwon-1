## 3. 어떻게 만들었나 — 설계 판단 3개

### ① 기준 시점을 한 곳에 모았다 — 새 파일 `sources.py`

**문제였던 것:** 기준 시점이 코드 여기저기서 만들어지고 있었습니다.
`agent.py`가 `date.today()`로 조회일을 만들고, `config.py`가 `ftc_year`를 따로 들고 있었습니다.
분기마다 갱신해야 하는 값인데 갱신할 자리가 흩어져 있으면 반드시 어긋납니다.

**한 것:** `commercial_area/sources.py`를 만들어 상수 두 개와 조립 함수 세 개를 모았습니다.

```python
SBIZ_PERIOD = "2026년 1분기"       # ⚠️ 분기마다 갱신하는 곳
SBIZ_REFERENCE_DATE = "2026-03-31"

def franchise_base_year(settings) -> int | None
def build_sources(settings, *, with_franchise) -> list[DataSource]
def build_description(settings, *, radius_m, store_total, ...) -> str
```

이제 **두 줄만 고치면** `scope.period` · `data_reference_date` · `sources[].period` · `description`이
함께 따라갑니다. 공정위 연도도 `settings.ftc_year` 하나에서 `sources[].period`와 `base_year`가
같이 나오므로 연도를 두 곳에 적을 일이 없습니다.

`build_description`을 여기 둔 이유는, 설명문의 내용이 "어느 자료를 어떤 단위로 읽는가"라
출처와 사실상 한 몸이기 때문입니다.

**조회일 폴백(`date.today()`)은 없앴습니다.** 자료 기준일이 아닌 값이 기준일 자리에 들어가던
문제였습니다. 다만 `meta.get("reference_date")`를 먼저 보는 앞단은 남겼습니다 —
원천이 나중에 날짜 필드를 추가할 수 있어서입니다(지금은 항상 상수 쪽이 쓰입니다).

### ② 누적 유인은 루프 밖에서 한 번만 계산했다

`build_middle_rows`는 중분류 75종을 도는 루프입니다. 여기서 대분류 HHI를 매번 다시 세면
75 × 대분류 재계산이 됩니다. 그래서 루프에 들어가기 **전에** 한 번만 만들어 두고 조회만 합니다.

```python
major_counts = count_by_major(stores)                      # 기존 함수 재사용
middle_counts_by_major: dict[str, list[int]] = {}
for code, entry in known.items():
    middle_counts_by_major.setdefault(entry.major_code, []).append(counts.get(code, 0))
cluster_diversity = {major: round(effective_categories(hhi(values)), 4) ...}
```

`hhi`·`effective_categories`·`count_by_major`는 이미 있던 함수를 그대로 썼습니다. 새 수식은 없습니다.

**합성 점수를 만들지 않았습니다.** 두 값에 가중치를 우리가 정하면 그게 곧 판단이 되고,
판단은 결정 에이전트 몫이라는 이 에이전트의 원칙(§"점수를 주지 않습니다")과 어긋납니다.

### ③ 계획에 없던 걸 하나 고쳤다 — 브랜드 캐시 파일명

**계획서에 없던 작업입니다.** `ftc_year`를 `2025`로 올리고 나서 발견했습니다.

브랜드 캐시 파일명이 `ftc_brands.json`으로 **연도가 없었습니다.** 이대로면 2024년에 받아둔
11,602개 목록이 그대로 읽히는데 `franchise.base_year`만 `2025`를 가리킵니다. **거짓 표기가 됩니다.**

`ftc_brands_<연도>.json`으로 바꿨습니다. 연도가 캐시 키에 들어가니 연도를 올리면 자동으로
새로 받습니다.

> 기존 `backend/cache/ftc_brands.json`(11,602개)은 이제 아무도 읽지 않습니다.
> **지우지 않고 뒀습니다** — 캐시라 지워도 되지만 확인 없이 파일을 지우지 않았습니다.

## 6. 사실대로 — 덜 한 것과 한계

이 절이 이 보고서에서 제일 중요합니다.

### ① 검증 실행을 노원이 아니라 강남에서 했습니다

계획서에는 "캐시로 실제 출력 확인 — 노원 좌표는 캐시에 있다"고 적었는데,
**실제로는 캐시에 노원이 없었습니다.** `cache/`에 있는 건 강남·송파 좌표였습니다.
그래서 캐시가 있는 강남 좌표(37.508816, 127.063201)로 돌렸습니다.

API를 새로 때리면 노원으로도 확인할 수 있지만, 확인하려던 건 "새 필드가 실제 출력에 실리는가"라
좌표가 어디든 같습니다. **다만 계획과 다르게 한 건 맞습니다.**

### ② 문서의 노원 예시 수치를 다시 측정하지 않았습니다

`DELIVERY`·`INDEX`의 노원 예시(`franchise.count 136` 등)는 **2024년 브랜드 목록으로 잰 값**입니다.
지금은 2025년 목록을 쓰므로 다시 돌리면 `count`가 조금 달라집니다.

값을 임의로 고치지 않고 **각주를 달았습니다.** 재측정하려면 노원 좌표로 API를 다시 불러야 하는데,
그건 이번 작업 범위(필드 추가)와 별개라 하지 않았습니다.
`independent_count`·`independent_ratio`는 기존 수치에서 뺄셈으로 나오는 값이라 그대로 적었습니다.

### ③ `SBIZ_PERIOD = "2026년 1분기"`는 코드에 박은 상수입니다

**API로는 검증할 수 없습니다.** 소상공인 오픈API 응답 39개 필드에 날짜가 하나도 없다는 걸
전수 확인했고, 그래서 공공데이터포털 파일데이터 페이지의 최신 분기를 보고 손으로 적었습니다.

즉 **이 값이 틀리면 코드가 알려주지 않습니다.** 분기마다 사람이 확인해야 합니다.
그래서 갱신 위치를 한 곳으로 모으고 `sources.py`·README에 눈에 띄게 적어 뒀습니다.
이게 지금 구조에서 할 수 있는 최선이고, 근본 해결은 아닙니다.

### ④ 프랜차이즈 판정은 여전히 `confidence: "low"`입니다

`independent_*`와 `base_year`를 더했지만 **판정 방식 자체는 그대로**입니다.
공정위 API에 반경 검색이 없어 브랜드명 11,724개와 상호명을 문자열로 대조합니다.
누락과 오탐이 구조적입니다. 개인사업자 수도 이 판정의 뺄셈이므로 **같은 오차를 물려받습니다.**
`base_year`를 넣은 건 정확도를 올린 게 아니라 **어긋남을 드러낸 것**입니다.

### ⑤ 커밋·푸시 안 했습니다

작업 트리까지만입니다. `develop`은 팀 공용 브랜치라 올리는 시점은 따로 판단이 필요합니다.
